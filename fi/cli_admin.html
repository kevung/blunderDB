Tietokannan hallinta

info — Tietokannan metatiedot

Näytä tietokannan metatiedot ja tilastot.

./blunderdb info --db <path> [--format <format>] [--estimate]

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --format — Tulostusmuoto: text tai json (oletus: text).

  • --estimate — Vastaa heti hyvin suuressa tietokannassa: yli 200 000 rivin jälkeen luku on arvio (yläraja), joka luetellaan JSONissa kentässä approximate ja tekstissä merkitään ”≈”, ja blunderit annetaan vain, jos niiden välimuistiin tallennettu määrä on yhä voimassa (muuten ei blunder_count-kenttää). Oletuksena jokainen rivi lasketaan; blunderien määrä tallennetaan välimuistiin tietokantaan ja lasketaan uudelleen jokaisen sitä mahdollisesti muuttavan kirjoituksen jälkeen (tuonti, analyysi, poisto, kynnyksen muutos).

Esimerkkejä:

./blunderdb info --db base.db

# Database Information
# ==================================================
# Path: /home/jean/bg/base.db
#
# Metadata:
#   Version: 2.31.0
#   User: Jean
#   Description: Matchs de tournoi 2025
#   Date of Creation: 2026-09-06 02:43:51
#
# Statistics:
#   Positions: 3859
#   Analyses: 3855
#   Matches: 11
#   Games: 61
#   Moves: 3766
#   Blunders: 142
#
# Thresholds (millipoints):
#   Error: 50
#   Blunder: 100

--format json lisää tiedoston alkuperän — issuance kantaa vesileiman, jos sellainen on, sekä tämän koneen liikkeeseenlaskijan identiteetin:

edit — Muokkaa metatietoja

Muokkaa tietokannan käyttäjänimeä, kuvausta tai kynnysarvoja.

./blunderdb edit --db <path> [options]

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --user — Uusi käyttäjänimi.

  • --description — Uusi kuvaus.

  • --clear-user — Tyhjennä käyttäjänimi.

  • --clear-description — Tyhjennä kuvaus.

  • --error-threshold — Virhekynnys millipisteinä: päätös, joka maksaa vähintään tämän verran, on virhe.

  • --blunder-threshold — Blunderin kynnys millipisteinä: virhe, joka maksaa vähintään tämän verran, on blunder.

  • --format — Tulostusmuoto: text (oletus) tai json ({"changes": [...]}).

Vähintään yksi muokkausvalitsin vaaditaan.

Esimerkkejä:

./blunderdb edit --db base.db --user "Marie" --description "Ma collection"
./blunderdb edit --db base.db --clear-description
./blunderdb edit --db base.db --error-threshold 20 --blunder-threshold 80

verify — Tarkista eheys

Tarkista tietokannan eheys ja valinnaisesti vertaa ottelua sen lähdetiedostoon.

./blunderdb verify --db <path> [--match <id>] [--mat <file.mat>]

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --match — Tarkistettavan ottelun tunnus.

  • --mat — Verrattava MAT-tiedosto (käytetään yhdessä --match:n kanssa).

  • --format — Tulostusmuoto: text (oletus) tai json (tilastot, orvot rivit, skeemapoikkeama ja mahdollinen ottelun tarkistus).

Ilman --match-valitsinta komento näyttää tietokannan yleiset tilastot. --match-valitsimen kanssa se tarkistaa ottelun tiedot ja voi verrata niitä alkuperäiseen lähdetiedostoon.

Jokainen ajo tarkistaa myös viite-eheyden: se laskee orvot rivit — pelit ilman ottelua, siirrot ilman peliä, siirtoanalyysit ilman siirtoa, analyysit ilman asemaa, kertauspäiväkirjan merkinnät ilman pakkaa tai ilman asemaa, harjoituskysymykset ilman istuntoa — ja tulostaa WARNING-rivin kokonaismäärällä, jos niitä on. Terve tietokanta vastaa Orphaned rows: none. Orpoja voi jäädä tietokantaan, jonka kirjoitti versio, joka ei valvonut vierasavaimia jokaisella yhteydellä, tai ennen kuin kertauspäiväkirjalla oli omansa; ne eivät kuulu mihinkään otteluun eivätkä mihinkään pakkaan ja vievät vain tilaa. Komento päättyy silti paluukoodiin 0.

Jokainen ajo vertaa myös skeemaa viite-DDL:ään ja luettelee taulut, sarakkeet ja indeksit, jotka tietokannasta puuttuvat. Tietokannan avaaminen lisää puuttuvat osat, kun se on mahdollista, ja vain kirjaa lokiin sen, mitä se ei voi lisätä (tyypillisesti UNIQUE-indeksin, jonka uudelleenrakentamisen kaksoisrivit estävät): tässä tuo puute tulee näkyviin, ja kysely, joka nimeää jonkin näistä osista, epäonnistuu, kunnes syy on korjattu. Terve tietokanta vastaa Schema: matches the reference DDL. Kuten orporivit, skeemapoikkeama on havainto, ei virhe: paluukoodi pysyy nollana.

Jokainen ajo tarkistaa lopuksi säännöt, jotka nykyinen DDL esittää mutta joita SQLite ei osaa lisätä jo olemassa olevaan tauluun: CHECK-rajoitteet (nopat välillä 0–6, tuplauskuutio ja pipit ei-negatiivisia, 0–15 ulos kannettua nappulaa, kertausarvosana välillä 1–4), Zobrist-tiivisteen, jota riviltä ei koskaan pitäisi puuttua, sekä yhden analyysin asemaa kohden. Skeemaversiosta 2.18.0 alkaen luotu tietokanta valvoo niitä; vanhempi voi yhä sisältää rivejä, jotka uusi tietokanta hylkäisi, ja juuri ne lasketaan tässä sääntö kerrallaan. Terve tietokanta vastaa Constraints: every row satisfies the current DDL. Yksi havainto lisää: mitään ei korjata ja paluukoodi pysyy nollassa.

Jokainen ajo laskee lopuksi uudelleen kaksi denormalisoitua laskuria, match.game_count ja game.move_count, niistä riveistä joita ne väittävät laskevansa, ja kertoo kuinka moni on eri mieltä ja kuinka paljon pahimmillaan. Molemmat kirjoitetaan kerran, tuonnin yhteydessä, sen mukaan mitä lähdetiedosto sisälsi, ja juuri ne näkyvät otteluluettelossa ja pelinäkymässä: pieni ero on useimmiten tuonti, joka ohitti sen mitä ei osannut muuntaa. Mitään ei kirjoiteta uudelleen — laskurin korvaaminen tallennetulla pyyhkisi juuri sen eron, jota kannattaa katsoa. Terve tietokanta vastaa Counters: game_count and move_count agree with the rows.

Esimerkkejä:

./blunderdb verify --db base.db
./blunderdb verify --db base.db --match 1
./blunderdb verify --db base.db --match 1 --mat original.mat

Käyttö vartijana. Paluukoodi on 0 riippumatta siitä, mitä komento löytää: tuomion kantaa --format json, ja skriptin on luettava laskurit itse.

{
  "stats": {
    "analysis_count": 3855,
    "blunder_count": 142,
    "game_count": 61,
    "match_count": 11,
    "move_count": 3766,
    "position_count": 3859
  },
  "orphans": {
    "games_without_match": 0,
    "moves_without_game": 0,
    "move_analyses_without_move": 0,
    "analyses_without_position": 0,
    "reviews_without_deck": 0,
    "reviews_without_position": 0,
    "training_items_without_session": 0
  },
  "orphan_total": 0,
  "schema_drift": {
    "missing_tables": null,
    "missing_columns": null,
    "missing_indexes": null
  },
  "schema_drift_count": 0,
  "constraint_violations": [
    {"name": "position.zobrist_hash NOT NULL", "count": 0},
    {"name": "position.dice_1 BETWEEN 0 AND 6", "count": 0}
  ],
  "constraint_violation_total": 0,
  "counter_drift": {
    "matches_with_wrong_game_count": 0,
    "games_with_wrong_move_count": 53,
    "worst_game_count_gap": 0,
    "worst_move_count_gap": 2

Kolme kenttää ansaitsee hälytyksen: orphan_total, schema_drift_count ja constraint_violation_total. Nollasta poikkeavina ne kuvaavat tietokantaa, joka on korjattava.

./blunderdb verify --db base.db --format json \
  | jq -e '.orphan_total == 0 and .schema_drift_count == 0 and .constraint_violation_total == 0'

counter_drift_total ei kuulu näihin, ja yllä oleva esimerkki osoittaa sen: sen tuottanut tietokanta oli juuri tuotu, ja siinä on jo 53 peliä, joiden siirtolaskuri poikkeaa siitä, mitä rivit sisältävät. Nämä laskurit tulevat lähdetiedostosta, eivät tietokannasta; poikkeama kertoo tuonnista, se ei ilmaise vioittumista. Katsokaa sitä, mutta älkää käyttäkö sitä kynnysarvona.

vacuum — Tietokannan tiivistäminen

Ottaa takaisin levytilan, jonka poistot (ottelut, turnaukset, siivoukset) ovat jättäneet: SQLite ei koskaan pienennä tiedostoa itsestään dataa poistettaessa, sitä on pyydettävä nimenomaisesti. Tämä on ainoa tapa käynnistää tiivistys — se ei tapahdu koskaan automaattisesti tietokantaa avattaessa, koska sen kustannus on suuressa tietokannassa arvaamaton.

./blunderdb vacuum --db <path>

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --format — Tulostusmuoto: text (oletus) tai json ({"size_before", "size_after", "reclaimed"}, tavuina).

Komento aloittaa suorituksella wal_checkpoint(TRUNCATE), jotta ennen tiivistystä näytetty koko on rehellinen, tarkistaa, että tiedoston vieressä on vapaata tilaa noin sen koon verran, kirjoittaa tiivistetyn tietokannan kopioon (VACUUM INTO), joka sitten korvaa tiedoston, ja suorittaa sen jälkeen ANALYZE-toiminnon virittääkseen kyselysuunnittelijan käyttämät tilastot. Jos jokin toinen ohjelma pitää tietokannan auki, tiedostoa ei korvata: komento tiivistää paikallaan (VACUUM), mikä vaatii noin kaksinkertaisen tiedostokoon verran vapaata tilaa. Jos levytila ei riitä, komento kieltäytyy käynnistymästä selkeällä viestillä sen sijaan, että riskeeraisi keskeytyneen tiivistyksen.

Ennen tiivistystä jokainen analyysi, jonka aiempi versio on vielä tallentanut JSON-muotoon, kirjoitetaan uudelleen kompaktiin binäärimuotoon (katso reencode).

Esimerkki:

./blunderdb vacuum --db base.db

# Compacting database...
#   Before: 128.4 MiB
#   After:  41.2 MiB
#   Reclaimed: 87.2 MiB

met — Tietokannan ottelun pääomataulukko

Luettelee, tuo tai valitsee ottelun pääomataulukon (MET), jolla gammonNet arvottaa tietokannan ottelutilanteet: Kazaross-XG2, sisäänrakennettu ja oletus, tai eksplisiittinen taulukko GNUbg:n .xml-muodossa. Jokainen lasketty analyysi tallentaa taulukkonsa; ottelutilanteen analyysi, joka on laskettu muulla kuin nykyisellä taulukolla, jätetään pois tilastoista. Taulukon vaihtaminen ei kirjoita mitään analyysia uudelleen.

./blunderdb met --db <path> [--import <fichier.xml> [--current] | --use <id>]

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --import — Tuo GNUbg:n .xml-taulukon. Jo olemassa olevaa tai Kazaross-XG2:n kanssa identtistä taulukkoa ei lisätä toista kertaa.

  • --current — --import-valitsimen kanssa: tekee tuodusta taulukosta nykyisen.

  • --use — Tekee annetun tunnisteen taulukosta nykyisen; 0 palaa Kazaross-XG2:een.

  • --format — Tulostusmuoto: text (oletus) tai json.

Komento tulostaa sen jälkeen tietokannan taulukot, nykyinen merkittynä merkillä *. Daemon tarjoaa samat toiminnot reiteillä met.list, met.import, met.setCurrent ja met.ofAnalysis, rajattuna kutsujan tenantiin.

Esimerkki:

./blunderdb met --db base.db --import Rockwell-Kazaross.xml --current

#     0  Kazaross-XG2
# *   1  Rockwell/Kazaross 25 point MET

reencode — Analyysien uudelleenkirjoitus kompaktiin muotoon

Analyysit tallennetaan kompaktiin binäärimuotoon, joka on noin puolet aiempien versioiden pakatun JSONin koosta ja moninkertaisesti nopeampi lukea uudelleen. Ennen tätä muotoa luotu tietokanta pysyy luettavana sellaisenaan: sen vanhemmat analyysit muunnetaan, kun ne kirjoitetaan uudelleen (niitä täydentävä tuonti, vacuum). reencode muuntaa ne kaikki tiivistämättä tiedostoa: hyödyllinen, kun levyllä ei ole tilaa vacuum-toiminnon kirjoittamalle tiivistetylle kopiolle, tai PostgreSQL-palvelimella, jossa vacuum-komentoa ei ole.

./blunderdb reencode --db <path>

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --format — Tulostusmuoto: text (oletus) tai json ({"rewritten"}, uudelleenkirjoitettujen analyysien määrä).

Muunnos etenee 2 000 analyysin erissä, jokainen omassa transaktiossaan. Keskeytyessään se jatkuu seuraavalla käynnistyskerralla siitä, mihin se jäi: jo muunnetut analyysit ohitetaan lukematta niitä uudelleen. Lukukelvoton analyysi jätetään ennalleen ja siitä ilmoitetaan lokissa. Se ei koskaan käynnisty itsestään. Daemon tarjoaa saman toiminnon reitillä maintenance.reencode, rajattuna kutsujan tenanttiin.

Esimerkki:

./blunderdb reencode --db base.db

#   Analyses rewritten: 15623468

maintenance — Tietokannan terveydentila

Yksi rivi jokaista ylläpitotoimintoa kohti: mitä se laskee, sen toiminto ja sen viimeisin ajo. Mikään ei käynnisty itsestään: ei tietokantaa avattaessa eikä tilaa luettaessa.

./blunderdb maintenance status --db <path>
./blunderdb maintenance count <opération> --db <path>
./blunderdb maintenance ids <opération> --db <path>
./blunderdb maintenance run <opération> --db <path>

Alikomennot:

  • status — Kaikki toiminnot, ilmaiset laskurit ja kunkin viimeisin ajo. Kallis laskuri näyttää (count on demand): count laskee sen.

  • count — Laskee toiminnon laskurin kustannuksista riippumatta.

  • ids — Luettelee tunnisteet, joita toiminto laskee (asemat tai ottelut); niiden määrä on count-komennon vastaus.

  • run — Käynnistää toiminnon ja kirjaa sen viimeisimmäksi ajokseen (valmistunut, peruttu tai epäonnistunut). Ctrl-C pysäyttää sen kahden erän välissä.

players — Pelaajan kirjoitusasut

Sama henkilö allekirjoittaa joskus eri tavoin tiedostosta toiseen (”Doe J.”, ”John Doe”). Alias kertoo, että nimi on kanonisen nimen toinen kirjoitusasu. Tietokannassa jo olevat ottelut säilyttävät tiedostojensa kirjoittamat nimet; tilastot, Pelaajat-taulukko ja haku pl"…" lukevat kaikki kirjoitusasut yhtenä henkilönä, ja jokainen seuraava tuonti tallentaa kanonisen nimen. Otteluikkunan pelaajien yhdistäminen luo samat aliakset.

./blunderdb players alias <add|list|remove|suggest> --db <chemin> [arguments]

Toiminnot:

  • add ALIAS CANONIQUE — ALIAS muuttuu CANONIQUE:n kirjoitusasuksi. Kanoninen nimi, joka on itse alias, seurataan sen omaan kanoniseen nimeen asti, ja ALIAS:ta osoittaneet aliakset siirtyvät kohteeseen CANONIQUE: vain yksi taso, ei koskaan ketjua.

  • list [--format text|json] — Aliakset kanonisen nimen mukaan järjestettyinä.

  • remove ALIAS — Unohtaa aliaksen; päättyy virheeseen, jos kyseessä ei ollut alias.

  • suggest [--format text|json] — Ehdottaa nimet, jotka eroavat vain kirjainkoon, aksenttien, välimerkkien tai sanajärjestyksen osalta, ja kanoniseksi nimeksi yleisimmän kirjoitusasun. Mitään ei tallenneta: jokainen ehdotus kirjoitetaan add-komentona, joka sen toteuttaisi.

Sormenjäljet. Ottelun sormenjäljet (match_hash, canonical_hash) säilyttävät tiedoston nimet: alias sovelletaan niiden jälkeen, vain tallennettuihin nimiin. Ennen aliaksen olemassaoloa tuotu tiedosto tunnistetaan siksi aina seuraavassa tuonnissa. Toisella kirjoitusasulla tuotu ottelu, jonka nopat ovat tietokannassa olevan ottelun nopat ja jonka nimet eroavat vain tunnettujen aliasten osalta, tunnistetaan samaksi otteluksi: sen analyysit rikastavat olemassa olevaa, toista ottelua ei luoda.

./blunderdb players alias add --db base.db "Doe J." "John Doe"
./blunderdb players alias suggest --db base.db

players merge — Ottelut-ikkunan pelaajien yhdistäminen samalla koodilla kuin palvelun reitti matches.mergePlayers: jokaisesta nimestä tulee kanonisen nimen kirjoitusasu, kuten yhtä monta players alias add.

./blunderdb players merge --db <chemin> --into <CANONIQUE> <NOM> [<NOM>...]

players swap — Vaihtaa ottelun kaksi pelaajaa, jotka tiedosto oli nimennyt väärässä järjestyksessä (reitti matches.swapPlayers). Mikään asema tai analyysi ei muutu: kukin pelaaja säilyttää tilastonsa, toisella paikalla. Vaihto hylätään, kun otteluun on avoinna litteroinnin luonnos, sekä blunderDB:ssä pelatulle ottelulle.

./blunderdb players swap --db <chemin> <ID_MATCH>

players main — Otteluikkunan pääpelaaja (reitit players.main.*). Ilman nimeä näyttää pääpelaajan; nimen kanssa se nimeää pelaajan ja vaihtaa yhdessä transaktiossa kaikki ottelut, joissa hän tai jokin hänen aliaksistaan on pelaaja 2; jokainen myöhempi tuonti asettaa hänet pelaajaksi 1. --dry-run näyttää vaihdettavat ottelut muuttamatta mitään; --clear poistaa pääpelaajan vaihtamatta mitään takaisin. Ottelu, jossa on avoin litterointiluonnos tai joka on pelattu blunderDB:ssä, jätetään ennalleen ja luetellaan erikseen.

./blunderdb players main --db <chemin> [--dry-run] [<NOM>]
./blunderdb players main --db <chemin> --clear

players matches — Pelaajan otteluiden tunnisteet kummalta tahansa puolelta ja kaikilla hänen aliaksillaan (reitti players.matchIds).

./blunderdb players matches --db <chemin> <NOM>

./blunderdb players merge --db base.db --into "John Doe" "Doe J." "J. Doe"
./blunderdb players swap --db base.db 42
./blunderdb players main --db base.db --dry-run "John Doe"

events — Tapahtuman kirjoitusasut

Samat toiminnot kuin players alias, tapahtumien nimille (tiedoston Event-kenttä). Tuonnissa ottelu, jonka tapahtuma on alias, sijoitetaan kanonisen nimen turnaukseen.

./blunderdb events alias add --db base.db "Open 2025" "Open d'automne 2025"
./blunderdb events alias list --db base.db

repair — Laske uudelleen se, mikä on johdettua

Laskee uudelleen sen, minkä tietokanta johtaa siitä mitä se tallentaa: jokaisen analyysin skalaarisarakkeet itse analyysistä, jonka projektio ne vain ovat; jokaisen aseman vaiheen ja pelityypin sen laudasta; ja jokaisen pistetilanteen Crawford-merkin siitä ottelusta, josta asema on peräisin, tai siitä XGID:stä, jonka mukana se tuli. Analyyseihin ei kosketa: uusiksi tehdään niistä johdetut arvot.

Tietokanta, joka on saanut analyyseja toisen tietokannan tuonnilla (import --type database, myös valvotun synkronointikansion kautta) tätä vanhemmalla versiolla, säilyttää nämä analyysit ilman sarakkeitaan tai niiden analyysien sarakkein, jotka ne korvasivat: niiden blundereita ei lasketa ja niiden pakotetut siirrot käyvät päätöksistä. repair vertaa näitä sarakkeita siihen, mitä tallennettu analyysi antaa, ja laskee eroavat uudelleen; sama sisältö lasketaan silloin kuin se olisi tullut transfer-komennolla.

./blunderdb repair --db <path>

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --format — Tulostusmuoto: text (oletus) tai json — yksi laskuri kierrosta kohden: repaired (analyysisarakkeet), phases (uudelleen luokitellut asemat) ja crawford (uudelleen tiivistetyt asemat) sekä signatures_unverified (allekirjoitetut kommentit, jotka uudelleentiivistys jättää vahvistamattomiksi: allekirjoitus kattaa aseman tunnisteen). Kukin kertoo todella muuttuneiden rivien määrän. --stats-valinnalla mukaan tulee match_stats (uudelleen lasketut ottelut). --move-errors lisää kentän move_errors (pisteytetyt siirrot).

  • --stats — Laskee lisäksi ottelukohtaiset tilastot kokonaan uudelleen.

  • --move-errors — Kirjoittaa lisäksi jokaiselle pelatulle siirrolle ekvityn, jonka se luovutti parhaaseen siirtoon nähden, luettuna sen aseman analyysistä (siirtotaulun sarake error_mp). Ajo on jatkettavissa: keskeytettynä se jatkaa siitä, mihin jäi; erittäin suurella kirjastolla se kestää useita minuutteja. Palvelinpuolella: matches.scoreMoves.

  • --duplicates — Ei suorita yhtään vaihetta: luettelee ottelut, joiden nopat ovat samat, yhdistämättä mitään (katso alla).

Ottelukohtaiset tilastot ovat jokaisen ottelun jokaiselle pelaajalle hänen päätöksensä, kertynyt virheensä, PR, blunderit, onni ja analyysiensä vallitseva alkuperä; tilastot lukevat ne sen sijaan, että kävisivät läpi jokaisen päätöksen uudelleen. Ne kirjoitetaan ottelun mukana tuonnissa ja tyhjennetään jokaisessa niitä muuttavassa muutoksessa (ottelu poistettu, pelaajat vaihdettu, jonkin sen aseman analyysi muutettu, blunder-raja siirretty); seuraava luku laskee puuttuvan. Aiemmasta versiosta migroitu tietokanta laskee ne kerran, ensimmäisellä avauskerralla. --stats tekee ne kaikki uudelleen: keino, jos tämä kirjanpito joskus menisi pieleen.

Todennäköiset kaksoiskappaleet. repair --duplicates vertaa otteluita noppien perusteella, ei koskaan nimien. Raportoidaan kaksi tapausta: sama pituus, sama alkutilanne ja samat nopat jokaisessa pelissä toisilla pelaajanimillä, sekä ottelu, jonka nopat jatkavat toisen noppia — katkaistu ja sitten täydennetty ottelu. Samoilla nopilla olevan parin alla tekstitulostus antaa players alias add -komennot, joiden jälkeen molemmat ottelut nimeäisivät samat pelaajat: vain yksi tulkinta, kun nimi on yhteinen molemmille (toinen nimi voi olla vain toinen pelaaja), muuten kaksi — paikka paikalta, sitten ristiin — numeroituina, joista vain yksi ajetaan. Uudemman ottelun kirjoitusasusta tulee alias, vanhemman kanoninen nimi. --format json palauttaa {"suspects": [...]}, kukin pari kentillä kind (same_dice tai longer), matchId, otherId, players, otherPlayers ja samoilla nopilla olevalle parille pairings: tulkintojen luettelo, kullakin omat aliases (alias, canonical). Ennen noppien sormenjäljen syntymistä tuotu ottelu saa sen samalla; se on tämän tilan ainoa kirjoitus.

Hyödyllinen sen jälkeen, kun tuodun analyysin lukutapaa on korjattu. Näin on käynyt jo kahdesti. XG-tuoja kirjoittaa ”ei tuplausta” kahdella tavalla, ja jälkimmäinen ymmärrettiin oikeana tuplauksena — sarake kantoi silloin tuplauksen virhettä, jota ei koskaan tapahtunut. Ja blunderDB:n itse laskema analyysi ei tiennyt mikä siirto oli pelattu, joten ilman analyysiä tuotu ottelu piti virheen nollassa kaikkialla ja PR:n arvossa 0,00; sarake lasketaan uudelleen ottelun siirroista. Lukutavan korjaus ei muuta mitään jo kirjoitetuissa riveissä; tämä komento tekee ne uudelleen.

Crawford-vaihe puolestaan koskee asemia itseään. Pistetilanne 1 tarkoittaa ”yksi piste jäljellä, ja tämä peli ON Crawford-peli”; 0 tarkoittaa ”yksi piste jäljellä, Crawford on takanapäin”. Niin kauan kuin tuojat eivät kirjoittaneet tätä eroa, jokainen Crawfordin jälkeinen asema tallennettiin Crawford-asemana ja luettiin siis kuollein tuplauskuutioin — juuri siellä, missä perässä oleva tosiasiassa tuplaa ensimmäisellä tilaisuudella. Pistetilanteen korjaaminen muuttaa aseman tiivisteen: rivi tiivistetään siis uudelleen ja sulautetaan oikeaan kaksoseensa, jos tietokannassa on jo sellainen — analyysi, kommentit, kokoelmat, Anki-kortit ja niiden kertaushistoria, ottelun siirrot sekä roskakorin merkinnät, jotka viittaavat siihen, seuraavat eloon jäänyttä riviä. Asema, johon mikään ottelu ei osoita, korjataan vain sen XGID:n sanan perusteella, jonka se toi toisesta ohjelmasta (XG, BGBlitz…): kun tuon XGID:n Crawford-kenttä sanoo, ettei peli ole Crawford-peli, ja XGID todella kuvaa tämän aseman. Toiseen suuntaan asema ilman ottelua, joka on tallennettu kummallekin puolelle arvolla 0, muuttuu arvoon 1, kun sen tuoma XGID on 1 pisteen ottelun XGID ja kuvaa sen: 1 pisteen ottelun ainoa peli alkaa yhden pisteen päästä tavoitteesta, joten se on Crawford-peli, kuten tuojat sen kirjoittavat. Pidemmän ottelun Crawfordin jälkeinen DMP pysyy arvossa 0: sen XGID kertoo tuon ottelun pituuden. XGID, jonka blunderDB on itse kirjoittanut uudelleen, vain toistaa tallennetun pistetilanteen eikä todista mitään. Jokainen muu asema ilman ottelua jätetään ennalleen: mikään ei ole ristiriidassa sen kanssa, mitä sen pistetilanne ilmoittaa.

Mikään ei käynnistä sitä automaattisesti, ja se on tarkoituksellista: kaikkien analyysisarakkeiden uudelleenkirjoittaminen tai asemien uudelleen tiivistäminen pelkästä tietokannan avaamisesta ei ole jotain, mitä työkalun tulisi tehdä käyttäjänsä selän takana.

Esimerkki:

./blunderdb repair --db base.db

# 42 analyses repaired.
# 7 positions reclassified.
# 3 positions rehashed onto the right Crawford sentinel.

delete — Poista tietoja

Poista ottelu ja kaikki siihen liittyvät tiedot (pelit, siirrot, analyysit).

./blunderdb delete --db <path> --type match --id <id> [--confirm]

Valitsimet:

  • --db — Tietokanta (pakollinen).

  • --type — Poistotyyppi: match (pakollinen).

  • --id — Poistettavan kohteen tunnus (pakollinen).

  • --confirm — Poista pyytämättä vahvistusta.

  • --format — Tulostusmuoto: text (oletus) tai json ({"match_id": N, "deleted": true}).

Esimerkkejä:

# Confirmation interactive, puis sans confirmation (scripts)
./blunderdb delete --db base.db --type match --id 1
./blunderdb delete --db base.db --type match --id 1 --confirm

healthcheck — Taustaprosessin tarkistus

Kysyy käynnissä olevalta serve-taustaprosessilta (ks. Headless-tila (palvelin)), onko se valmis: yksi GET /readyz-pyyntö, paluukoodi 0, jos taustaprosessi vastaa 200 (tallennus tavoitettavissa, skeema odotetussa versiossa), muuten 1 — tallennus ei tavoitettavissa, vanhentunut skeema tai osoitteessa ei kuuntele mikään. Tietokantatiedostoa ei avata.

./blunderdb healthcheck [--addr host:port] [--timeout 2s]

Valitsimet:

  • --addr — Osoite, jota taustaprosessi kuuntelee (oletus BLUNDERDB_ADDR, muuten :8080). Osoite ilman isäntää (:8080) tai yleisisännällä (0.0.0.0, [::]) tarkistetaan loopback-liitännän kautta.

  • --timeout — Aika, jonka jälkeen tarkistus luovuttaa (oletuksena 2s).

Tämä on komento, jonka konttikuvan HEALTHCHECK suorittaa (distroless-kuva, ilman curl-ohjelmaa); myös cmd/serve-hakemistosta käännetty serve-binääri ymmärtää sen. Se sopii yhtä hyvin skriptiin tai systemd-yksikköön.

Esimerkki:

./blunderdb serve --db base.db --addr 127.0.0.1:8080 &
./blunderdb healthcheck --addr 127.0.0.1:8080 && echo "démon disponible"

# ready

Epäonnistuessa syy tulostetaan, ja docker inspect näyttää sen unhealthy-tilassa olevalle kontille:

Error: healthcheck: http://127.0.0.1:8080/readyz answered 503 Service Unavailable (version_mismatch)

mcp — Tietokannan tarjoaminen tekoälyavustajalle

Tarjoaa tietokannan työkalut tekoälyavustajalle Model Context Protocol -protokollan kautta vakiosyötteen ja -tulosteen yli: avustaja käynnistää komennon. Työkalut hakevat asemia komentorivin kieliopilla, lukevat aseman ja sen analyysin, selittävät virheen, laskevat pelaajan tilastot, luettelevat ottelut, turnaukset ja kokoelmat sekä esittävät tietovisan kysymyksen. Ne vain lukevat, paitsi valitsimella --write. Täydellinen luettelo ja demonin HTTP-vastine: Työkalut tekoälyavustajalle (MCP).

./blunderdb mcp --db base.db [--write]

Valitsimet:

  • --db — Tietokantatiedosto (pakollinen).

  • --write — Tarjoaa myös kirjoittavat työkalut: aseman tallennus, sen kommentointi, kokoelman luonti ja täyttö. Mitään ei poisteta.

Kuten call, komento siirtää vanhemman tietokannan skeeman avattaessa, myös ilman --write-valitsinta.

Esimerkki: tietokannan ilmoittaminen Claude Codelle.

claude mcp add blunderdb -- blunderdb mcp --db /chemin/vers/base.db

completion — Shell-täydennys

Tulostaa vakiotulosteeseen täydennysskriptin alikomentojen nimille. Jokaiseen skriptiin sisällytetty komentoluettelo generoidaan samasta taulukosta, jota myös blunderdb help ja main.go:n reititys (handlers()) lukevat: uusi alikomento tarjotaan siis täydennyksessä heti, kun se on kytketty, eikä mitään tarvitse ylläpitää käsin.

./blunderdb completion <bash|zsh|fish>

Esimerkkejä:

# bash
source <(blunderdb completion bash)
blunderdb completion bash | sudo tee /etc/bash_completion.d/blunderdb > /dev/null

# zsh : un répertoire déjà sur $fpath
blunderdb completion zsh > "${fpath[1]}/_blunderdb"

# fish
blunderdb completion fish | source

Paketit asentavat tämän automaattisesti: .deb/.rpm (nfpm) ja AUR-paketti tuottavat kolme skriptiä paketoidusta binääristä käännöshetkellä, ja Homebrew-cask suorittaa blunderdb completion <shell> kerran asennuksen yhteydessä komennolla generate_completions_from_executable. Mitään ei tallenneta arkistoon, joten täydennys ei voi koskaan poiketa alikomentotaulukosta.

version — Näytä versio

Näyttää blunderDB:n version ja tämän binäärin kirjoittaman tietokantaskeeman version; se on ensimmäinen asia, joka liitetään virheraporttiin.

./blunderdb version
# blunderDB version 0.36.0 (database schema 2.31.0)

Приложение: Модель статистики — выравнивание XG / gnuBG / blunderDB

Формальные определения

PR (Performance Rating)

PR — это средняя ошибка эквити на учитываемое решение, умноженная на 500, как в eXtreme Gammon:

\[\mathrm{PR} = \frac{\sum_i |\mathrm{error}_i|}{\mathrm{N_{counted}}} \times 500\]

  • Числитель — сумма ошибок в нормализованном эквити (EMG по счёту матча), каждая из которых относится к ходу, сыгранному в своём матче.

  • Знаменатель \(N_\text{compté}\) считает решения по правилам XG: неформальные ходы фишками, предложенные удвоения, взятия и отказы, а также близкие «без удвоения». Эти правила, их обоснование и ограничения подробно описаны в PR (Performance Rating).

  • Множитель 500 — соглашение XG. Это не перевод в миллипункты: средняя ошибка 0,010 эквити — то есть 10 миллипунктов (mpt) — даёт PR 5,0. Ошибки же отдельной позиции удобно читать в миллипунктах, то есть в тысячных долях эквити: порог блундера ниже, поисковые фильтры e> и E>, гистограмма величин на панели Stats.

Snowie Error Rate

ER Snowie использует тот же числитель, что и PR, но знаменатель — число ходов фишек обоих игроков, включая вынужденные ходы, без какого-либо правила подсчёта:

\[\mathrm{SnowieER} = \frac{\sum_i |\mathrm{error}_i|}{N_\text{P1} + N_\text{P2}} \times 500\]

Источник: gnubg/formatgs.c:415–424.

Snowie ER стабильнее между программами, поскольку его знаменатель не зависит ни от каких правил подсчёта решений. Он служит метрикой для перекрёстной проверки XG ↔ gnuBG ↔ blunderDB.

Важно

Фильтр «Игрок» действует только на числитель. Выбор игрока ограничивает суммируемые ошибки его собственными решениями, но знаменателем остаётся число ходов шашками обоих игроков по матчам, которые оставил фильтр. Именно это отличает Snowie ER от PR и объясняет следующее свойство: в базе, содержащей только матчи между двумя игроками, сумма их двух Snowie ER в точности равна нефильтрованному Snowie ER.

Примечание

Snowie ER игрока обычно составляет около половины его PR, так как знаменатель включает ходы обоих игроков, тогда как PR использует только решения данного игрока.

Потеря MWC (Match Winning Chance)

Потеря MWC выражает в процентных пунктах вероятности выигрыша матча суммарный эффект ошибок игрока. Для каждого решения ошибка EMG преобразуется в MWC через таблицу MET (Match Equity Table) при текущем счёте:

\[\mathrm{MWCLoss} = \sum_i \mathrm{eq2mwc}(\mathrm{erreur}_i, \mathrm{score}_i)\]

Взятие или отказ пересчитывается по кубу до удвоения, как и решение удваивающего и как это делает XG. Пересчёт и его ограничения подробно описаны в Потеря MWC на решение и график матча.

Удача (luck)

Удача броска — это разница между тем, что дали кости, и тем, что они дают в среднем:

\[\mathrm{luck} = \mathrm{eq}(\text{лучший ход при выпавшем броске}) - \frac{1}{36}\sum_{d} \mathrm{eq}(\text{лучший ход при } d)\]

сумма берётся по 36 исходам броска (30 недубльных бросков для первого хода партии, который не может быть дублем). Положительное значение означает удачный бросок. Ссылка: gnubg/analysis.c:199–269 (LuckNormal / LuckFirst, cubeful-оценка на 0 ply).

Важно

blunderDB никогда не вычисляет удачу: встроенный оценщик служит не для этого. Он берёт как есть значение, записанное инструментом, который анализировал матч, — ErrLuck у eXtreme Gammon, свойство LU у gnuBG, — предварительно убедившись, что оба используют одно соглашение (та же единица, положительное = повезло).

Практические следствия:

  • Форматы, которые не переносят удачу (BGF, Jellyfish .mat), не дают никакого значения.

  • У уже импортированных матчей её тоже нет: до версии схемы 2.15.0 удача не сохранялась, и восстановить её по базе нечем. Чтобы её получить, исходные файлы нужно импортировать заново.

  • Отсутствующее значение означает неизвестно, но не ноль: ноль — это по-настоящему нейтральный бросок. Поэтому средние удачи делятся только на число бросков, чья удача известна.

  • Матч, в котором у всех бросков удача была бы ровно нулевой, считается в этом отношении непроанализированным (eXtreme Gammon пишет 0 и для «нейтрально», и для «не вычислено»): его броски остаются неизвестными. У gnuBG различие явное — неоценённый бросок несёт LU[-inf] — и такие броски тоже остаются неизвестными, а не превращаются в значение.

Победы и поражения

blunderDB не хранит победителя на уровне матча: хранятся только очки каждой партии. Поэтому результат выводится при отображении, суммированием очков по местам:

  • Матч до N очков — победитель = игрок, набравший N. Если никто не набрал, матч не завершён (обрезанный журнал, отказ от игры) и не засчитывается ни в победы, ни в поражения — никому.

  • Игра на деньги (без цели) — победитель = тот, кто взял больше очков; при равенстве ни победы, ни поражения. Это соглашение gnuBG о результате сессии (+1 / 0 / −1, gnubg/relational.c).

Следствие, которое стоит помнить при чтении вкладки «Игроки»: победы + поражения могут быть меньше числа матчей. Разница — это незавершённые матчи.

Ошибки и бландеры

Решение засчитывается как ошибка, как только связанная с ним ошибка эквити достигает порога ошибки библиотеки, и как бландер, как только она достигает её порога бландера. Оба задаются на вкладке Библиотека настроек и по умолчанию равны 0,050 и 0,100 EMG (50 и 100 миллипунктов). Сравнение включающее: ошибка ровно в 0,100 — это бландер при пороге по умолчанию, на всех экранах (разбивка по действиям с кубом, подробности матча, таблица игроков), и та же пара служит счётчику строки состояния и списку, предлагаемому после импорта.

Эти пороги свои у каждой библиотеки, а значения по умолчанию свои у blunderDB: gnuBG классифицирует ходы по трём ступеням (0.03 сомнительный, 0.06 плохой, 0.12 очень плохой — gnubg/gnubg.c:281–286), а не по одной категории, а eXtreme Gammon проводит свои границы на 0,020 и 0,080. Настройка предлагает три пресета: blunderDB (0,050 и 0,100), XG (0,020 и 0,080) и GNUbg (0,040 и 0,080).

Известные остаточные расхождения

Четыре игрока эталонных матчей расходятся сильнее; в каждом случае причина в том, что файл не содержит нужных данных:

  • Непроанализированный ход (два игрока). Для хода, который XG не оценил, он записывает ошибку −1000 и не включает его в подсчёт; при импорте это значение не читается, и blunderDB оценивает ход по сохранённым кандидатам. blunderDB считает на одно решение больше; PR расходится до 0,09, потеря MWC — до 0,45 очка.

  • Съём, оценённый вне файла (один игрок). XG считает решением съём, для которого сохранённые кандидаты охватывают все допустимые ходы с одинаковым эквити: он оценил его по оценкам, которые файл не хранит. blunderDB считает на одно решение меньше; PR расходится на 0,02.

  • Сумма ошибок фишками (один игрок). Количества и куб совпадают; сумма ошибок сохранённых ходов превышает итог XG по фишкам на несколько миллипунктов (2,150 против 2,147).

Примечание

Файлы SGF (gnuBG) не содержат альтернатив для вынужденных ходов, поэтому blunderDB не может распознать все вынужденные ходы при импорте SGF. Это создаёт структурное расхождение по Snowie ER (немного другой знаменатель).

Проверка собственных данных

Если ваши значения PR или MWC расходятся с числами XG, проверьте следующее:

  1. Полные анализы — PR можно вычислить только по позициям, у которых есть анализ. Позиции без анализа засчитываются как нулевая ошибка, но не входят в \(N_\text{compté}\).

  2. Версия XG — XG может менять расчёты между версиями. blunderDB выровнен с поведением, наблюдаемым в последних версиях.

  3. Формат импорта — файлы SGF gnuBG дают более значительные расхождения по кубу (см. таблицу выше), поскольку файл не включает полные анализы для всех решений по кубу.

  4. Миграция базы данных — После обновления blunderDB существующие базы данных мигрируются автоматически. Сделайте резервную копию перед открытием базы данных с новой версией.

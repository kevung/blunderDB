# T0.7 — Issue jumelle : les importeurs écrivent la sentinelle Crawford ; `repair` rehache [M]

CONTEXT.md (« Away score ») distingue away `0` (un point à faire, partie Crawford
derrière) de away `1` (cette partie EST la Crawford) ; `domain.AwayScores` ne calcule que
`matchLength - score`, qui vaut `1` pour les deux cas indifféremment. Les trois
importeurs écrivent donc `1` sur toute position à un point de la victoire, y compris les
parties post-Crawford, où `MatchStateFromPosition`
(`pkg/blunderdb/engine/gammonnet/domaineval.go:325-357`) lit alors Crawford à tort et le
videau mort. Une transcription (T0.2), elle, écrira la sentinelle correctement dès le
départ (ADR-0044 §7) : sans ce correctif, ses positions post-Crawford ne se déduppliquent
jamais avec leurs jumelles importées, faussement à away 1.

**Tranche verticale** : Go (`ingest` + `database`) → CLI (`repair`) → tests. Pas de Svelte
ni de binding Wails nouveaux : `repair` existe déjà côté CLI/GUI/serveur.
**Prérequis** : — (indépendante du reste du plan).
**Livrable** : un import XG, GnuBG ou BGF d'une partie post-Crawford écrit away `0`, pas
`1` ; `blunderdb repair` rehache les positions déjà importées qui portaient la sentinelle
fausse.

## Travail

  `AwayScoresWithCrawford(matchLength, score0, score1 int, isCrawfordGame bool) [2]int` —
  calcule `AwayScores` puis force à `0` toute valeur égale à `1` quand `isCrawfordGame` est
  faux (post-Crawford), la laisse à `1` sinon (c'est la partie Crawford elle-même).
- `pkg/blunderdb/ingest/gnubgmap.go:101` (`createPositionFromGnuBG`) : le paramètre `game
  *gnubgparser.Game` porte déjà `CrawfordGame bool` (utilisé pour la conversion MWC→EMG en
  `pkg/blunderdb/ingest/gnubg.go:194,253`, jamais pour le score) — remplacer
  `domain.AwayScores(matchLength, game.Score[0], game.Score[1])` par
  `domain.AwayScoresWithCrawford(matchLength, game.Score[0], game.Score[1],
  game.CrawfordGame)`.
- `pkg/blunderdb/ingest/bgfmap.go:212` (`createPositionFromBGF`) : le paramètre `rules
  bgfRules` porte déjà `.crawford` (lu par jeu depuis `isCrawford`,
  `pkg/blunderdb/ingest/bgf.go:95`, jamais utilisé pour le score) — même remplacement avec
  `rules.crawford`.
- `pkg/blunderdb/ingest/xgmap.go:75` (`createPositionFromXG`) : `xgparser.Game` ne porte
  aucun indicateur par partie, il faut donc le dériver. Ajouter `isCrawfordGame(matchLength,
  gameIndex int, games []xgparser.Game) bool` dans `xgmap.go` (première partie dont un score
  initial vaut `matchLength-1`), sur le modèle de l'algorithme déjà écrit côté test en
  `pkg/blunderdb/engine/gammonnet/integration_gate_test.go:327-343`, puis appeler
  `domain.AwayScoresWithCrawford`. Le mappeur connaît déjà toutes les parties avant de
  construire les positions : seul l'index de partie descend en plus.
- `pkg/blunderdb/storage/positions.go` (interface `PositionStore`, modèle
  `ReclassifyDerived`, `:48-57`) : nouvelle méthode `RepairCrawfordSentinel(ctx
  context.Context, scope string) (int, error)` — relit chaque position à away `1`,
  retrouve sa partie et son match (`move.position_id` → `game.match_id` → `game_number`),
  recalcule si elle est *réellement* la partie Crawford de ce match ; si non, corrige l'away
  à `0` et **rehache** par le chemin de dédup (`Save`) plutôt qu'un `UPDATE` en place, ce qui
  fusionne avec une position déjà correcte. Dans les deux backends.
- `pkg/blunderdb/database/db_gamephase.go` : `Database.RepairCrawfordSentinel()` délègue au
  store comme `RepairGamePhases` (`:20-27`) le fait déjà.
- `internal/cli/cli_repair.go` : `runRepair` l'appelle à la suite de `RepairGamePhases`
  (`:74-77`), même affichage et même champ JSON.
- `internal/server/handlers_positions.go` : route jumelle de
  `/v1/positions.reclassifyPhases` (`:101-103`) appelant la même méthode.

  correctement hachée à away `0` existait déjà pour ce même plateau, les deux fusionnent
  en une seule ligne.
- `blunderdb repair --db <fixture>.db --format json` : le champ du nouveau compteur est
  présent et cohérent avec le nombre de positions corrigées.

## Invariants touchés

- « Positions are identified by Zobrist hash » : le correctif change une valeur qui FAIT
  partie du hash (l'away score, contrairement à `has_jacoby`/`has_beaver`), d'où le
  rehachage par un `Save` et jamais un `UPDATE` en place.
- « Schema changes require bumping DatabaseVersion » : **ne s'applique pas** (aucune
  colonne, aucune migration ; un correctif de données comme `RepairGamePhases`).
- « CLI/GUI/server parity » : `RepairCrawfordSentinel` vit sur `PositionStore` (le contrat
  `storage`), comme `ReclassifyDerived` — CLI, binding GUI et route serveur l'appellent
  tous les trois, sans logique dupliquée.

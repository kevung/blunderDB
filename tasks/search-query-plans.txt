EXPLAIN QUERY PLAN — blunderDB, recherche sur une bibliothèque réelle (schéma 2.28.0 → 2.30.0)
==========================================================================================

Remplace la version v2.0.0 de ce fichier (345 positions), dont les plans ne disaient rien
d'une grande base : le planificateur ne choisit pas les mêmes index à 15 M de lignes.

Corpus    bibliothèque réelle de tournois : 15 625 009 positions, 15 623 468 analyses,
          16,6 M coups ; fichier de 12,8 Go en 2.28.0.
Moteur    modernc.org/sqlite v1.59.0 (SQLite pur Go), cache_size 64 Mo, mmap 256 Mo,
          une connexion ; Ryzen 6850U, NVMe, 14 Go de RAM.
Requêtes  chaque filtre passe par Search().Count puis Search().FindIDs(limit 100) du
          magasin SQLite (sqlshared/search.go), plan relevé par EXPLAIN QUERY PLAN sur
          la requête réellement émise.
Mesure    cache chaud : deux passes, la seconde retenue. Les écarts de ±10 % sont du bruit
          (un même plan a varié de 4,4 à 5,1 s d'une passe à l'autre).
2.28.0    la base telle qu'importée : statistiques échantillonnées par
          RefreshSearchStatistics (PRAGMA analysis_limit=1000, « 1001 lignes par clé »
          sur presque tous les index).
2.30.0    la même base migrée, ANALYZE complet compris (finishLargeLibraryWave).

3. Statistiques du planificateur
--------------------------------

La migration rafraîchit les statistiques par un ANALYZE complet. Même base 2.30.0, trois
jeux de statistiques :

  filtre              périmées (2.28.0)   échantillonnées (limit 1000)   ANALYZE complet
  S, Count                 862 ms               921 ms                     120 ms
  O, Count                 917 ms               836 ms                     128 ms
  D + score, Count        2,69 s               2,70 s                      137 ms
  race + o, page             1 ms                 —                        846 ms

L'ANALYZE complet coûte 30 s cache chaud, 60 s cache froid, contre 18 min pour les deux
passes de rétro-remplissage. Sans lui, la migration laissait des statistiques qui ne
connaissent pas les index créés ; c'est ce qui avait fait croire à une régression de
Count c (4,7 → 20 s) et D + p (2,7 → 12,8 s) : ces mesures-là étaient de plus prises
cache froid, juste après la migration. Cache chaud, Count c ne bouge pas (4,4 → 4,7 s).

Contrepartie acceptée : avec des estimations justes, la première page de race + o trie
304 044 candidats d'idx_position_off au lieu de s'arrêter à 100 dans
idx_position_game_phase (1 ms → 846 ms). Le même plan sort de tout ANALYZE complet
(ensureSearchStats sur une base sans statistiques, Vacuum) : c'est une limite du coût
de LIMIT + ORDER BY id dans le planificateur, pas de la migration.


4. Insertion
------------

Banc : 200 000 positions et leurs analyses recopiées dans une transaction annulée
(c6/insert-bench.sql ; en 2.30.0 avec match_date, analysis_engine, analysis_depth,
creation_date).

                    2.28.0 (froid / chaud)   2.30.0 (deux passes)
  INSERT position       46,7 / 40,5 s          15,7 / 12,4 s
  INSERT analysis       54,0 / 27,8 s          34,1 / 35,4 s

position gagne trois fois (cinq index de moins) ; analysis paie les trois index de
provenance et l'index couvrant joueur 2, plus large que win2 + gammon2.

# The evaluator batches positions, one per lane, and keeps the scalar sum order

Status: accepted.
See also: ADR-0011, ADR-0033

## Context

A 2-ply decision cost 5.5 s serially, 97.6 % of it in the forward pass; Go does not
auto-vectorise. A stored gammonNet analysis must be reproducible on another machine, otherwise
"stale" (`AnalyzeStaleGammonNet`) has no definition. The fastest kernels (FMA, tree reductions,
multiple accumulators, int8) each move the result — by ~3e-9 to 4.8e-7, within the gold
tolerance, above zero, and differently on every architecture. Vectorising over positions
instead brought the decision to 0.277 s serial, 0.072 s on all cores, with no equity moved by
one bit.

## Decision

1. **The kernel vectorises over positions, never over the reduction.** A batch is
   `EvalBatchWidth` positions, one per SIMD lane; each lane accumulates
   `bias[i] + Σ_j w[i][j]·act[j]` in float32, in ascending `j`, multiply and add as two
   operations (the explicit `float32(a*b)` is the fusion barrier). No FMA (`vfmadd*`, `fmla`),
   no reassociation, no float64 accumulation. Each position's result is bit-identical to the
   scalar loop.
2. **Batch width is fixed and part of the contract.** A partial batch is filled by duplicating a
   position, never with zeros.
3. **One result, several code paths, one seam.** The AVX2 kernel (amd64, Go assembly generated by
   avo) and a pure-Go fallback of the same layout, which is the reference of the bit-identity
   test on every CI runner. `BLUNDERDB_GAMMONNET_KERNEL=go|avx2|neon` selects one; the default
   is the best available; **a requested-but-unavailable kernel is an error at load**, never a
   silent fallback. No cgo. arm64 runs the fallback: a NEON kernel is added only once it can be
   run through the identity test on real arm64 hardware — never written blind.
4. **Skipping zero inputs is allowed** (`acc + w × 0.0 = acc` in IEEE 754), proved by the same
   identity test, not assumed.
5. **Parallelism is production behaviour.** The analysis batch runs positions across `NumCPU`
   goroutines, each reusing one serial `Searcher`; the live panel runs one search with
   `WithWorkers(NumCPU)` over the root's rolls. The two never stack. Both stay bit-identical to
   the serial search because the weighted sum over the 21 rolls is taken serially in ascending
   roll order.
6. **Nothing here changes what the engine plays.** Move filters, transposition tables, a
   distilled or quantised network are new Configurations, decided upstream (ADR-0011 rules 7–8).

## Consequences

- Assembly enters the tree with a pure-Go twin kept in lockstep; the identity test is the
  invariant, not the gold suites (they tolerate 1e-6 and would let an FMA through).
- A further ×1.5–2 on the kernel is deliberately left on the table; taking it means reversing
  this decision on stored-analysis reproducibility, not tuning.
- Other backends are ADR-0033's subject.

## Guard

`pkg/blunderdb/engine/gammonnet/kernel_identity_test.go` (`==` on every bit against the Go
fallback); `TestParallelSearchIsBitIdentical` (`search_test.go`); `parity_test.go`.

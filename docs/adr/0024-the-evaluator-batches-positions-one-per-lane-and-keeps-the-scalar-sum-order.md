# The evaluator batches positions, one per lane, and keeps the scalar sum order

## Status

proposed — decided 2026-09-02 in a grilling session, to be accepted when the batched kernel
passes its bit-identity test. Executes the bounded follow-up ADR-0011 left open ("the kernel
vectorises across the BATCH dimension, not across the reduction … a bounded follow-up with a
measured target"), and turns two of ADR-0011's statements into things the code actually does:
intra-search parallelism, which it called a *requirement*, is today never enabled outside
the tests. Plan and measurements: `tasks/gammonnet-perf/README.md`.

## Context

Measured on 2026-09-02 (Ryzen 7 PRO 6850U, Go 1.25.13): one forward pass of the
`strehl-prob5-512-512-256-128` network costs 404 µs, and a canonical 2-ply k=12 decision
5.5 s serially, of which `Evaluator.Evaluate` is 97.6 %. The reference C evaluates the same
network at 41 µs per position with a batched kernel — activations feature-major, 32 positions
per batch, one per lane, which gcc vectorises. Go does not auto-vectorise, and ADR-0011
measured the pure-Go batched loop at ×0.97.

Two facts frame the decision. First, the port's value is the proof that it *is* gammonNet:
network parity at 5.960e-08 against the C, gold searches within 1e-6, and — more important to
the product — a gammonNet analysis stored in a `.db` must be reproducible on another machine,
otherwise "stale" (`AnalyzeStaleGammonNet`) has no definition. Second, the fastest kernels
(FMA, tree reductions, multiple accumulators, int8) each move the result: upstream measured
FMA contraction at ~3e-9 on an equity and reassociation at 4.8e-7 — within the gold
tolerance, above zero, and different on every architecture.

## Decision

1. **The kernel vectorises over positions, never over the reduction.** A batch is `B`
   positions, one per SIMD lane; each lane accumulates `bias[i] + Σ_j w[i][j]·act[j]` in
   float32, in ascending `j`, with multiply and add as two separate operations. No FMA
   (`vfmadd*`, `fmla`), no reassociation, no float64 accumulation. The result of a position is
   therefore **bit-identical** to the scalar loop it replaces, and to the C reference at the
   same 5.960e-08 already proved.
2. **Batch width is fixed and part of the contract.** A partial batch is filled by
   duplicating a position, never with zeros, so a caller never reasons about the tail and a
   duplicated lane is checkable against its twin.
3. **Three code paths, one result**: AVX2 (amd64) and NEON (arm64) written as Go assembly
   generated by avo, and a pure-Go fallback of the same layout that is the reference of a
   bit-identity test run on every CI runner. `BLUNDERDB_GAMMONNET_KERNEL=go|avx2|neon`
   selects one explicitly for tests and diagnosis; the default is the best available. No
   cgo: the `serve` image is `CGO_ENABLED=0` and ADR-0011 chose the Go port to avoid it.
4. **Skipping zero inputs is allowed** — the 196-feature thermometer encoding is ~80 % zeros
   and `acc + w × 0.0 = acc` in IEEE 754 — and is proved by the same bit-identity test, not
   assumed.
5. **Parallelism is production behaviour**: the analysis batch runs positions across
   `NumCPU` goroutines, each reusing one serial `Searcher`; the live panel runs one search
   with `WithWorkers(NumCPU)` over a work queue of rolls. Both stay bit-identical to the
   serial search because the weighted sum over the 21 rolls is still taken serially in
   ascending roll order.
6. **Nothing in this decision changes what the engine plays.** Equity-threshold move filters,
   node transposition tables, a distilled smaller network, int8 quantisation are each a
   different Configuration in the sense of `CONTEXT.md`; they are decided upstream in
   gammonNet with its strength gauge, and the port follows with a new `EngineVersion`.

## Consequences

- Assembly enters the tree, generated, with a pure-Go twin that must stay in lockstep; the
  bit-identity test is the invariant, not the gold suites (which tolerate 1e-6 and would let
  an FMA through).
- **Amended 2026-09-02 while executing F1 (#133): decision 3 named avo for both kernels, and
  avo has no arm64 back end** (v0.6.0 ships `avo/x86` and nothing else; confirmed by the P1
  research note). F1 therefore ships the AVX2 kernel plus the pure-Go fallback, and arm64
  runs the fallback — correct, simply not accelerated. The NEON twin is a follow-up and must
  be hand-written Plan 9 arm64 assembly (`simd/archsimd` is Go 1.26+, arm64 only from 1.27;
  this project is on 1.25). It is deliberately not written blind: nothing in this repository's
  toolchain can execute arm64 code, so a NEON kernel written here could not be put through
  `kernel_identity_test.go`, and shipping an unverified fast path is the failure mode #133's
  fourth acceptance criterion exists to prevent. The kernel seam takes one more entry when
  someone can run the test on a real arm64 machine.
- A ×1.5–2 on the kernel is deliberately left on the table. Revisiting it means revisiting
  cross-machine reproducibility of stored analyses, and that is this ADR's decision to
  reverse, not a tuning knob.
- Once the kernel is ×7 faster, the 2.4 % of a decision spent outside the network becomes
  15–20 %: allocation per call, reflective stable sorts, quadratic move dedup, cube
  bisections. They go to the backlog with a post-kernel profile, and are not touched before.

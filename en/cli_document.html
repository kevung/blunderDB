Importing the positions of a document

What it is for

A book you own — problem book, collection, article — shows positions as diagrams, in the order of study. The document command files them in a collection of the database, in that order, so that you can study them again along with the rest of the library. The interface follows the same path in an assistant (The interface’s import assistant); the command line is described here.

The work goes through an intermediate file, the relevé: a JSON file that lists the positions read in the document. You reread it, correct it if needed, then import it. Reading a document writes nothing to the database; only importing a relevé writes.

What is read, what is refused

document analyze reads these kinds of documents:

  • a PDF whose diagrams are drawn with the eXtreme Gammon board font (the PDFs printed by XG): each diagram is text there, which the command decodes exactly, glyph by glyph;

  • a PDF whose diagrams are drawn with a Snowie board font (the Atchoum family, for example “AtchoumSnowie4Normal”): the checkers are read from the shapes of the glyphs the PDF embeds, whatever the version of the font; the printed pips confirm the reading. The score is not printed there: the context remains to verify;

  • a scanned book: a PDF whose pages are made of images, with or without a text layer, or its pages as images (a folder of PNG or JPEG files, one page per file, read in the order of their names, or a single image). Diagrams are read there by their structure (see Scanned books);

  • a written document, DOCX, ODT, EPUB or HTML page: its images are read one by one in the order of the text, each as a page image. The page number of an entry is then the rank of its image among those read, its chapter the title that precedes it, and it is cited “fig. 12” or “Chapter 3, fig. 12”. The paragraph before the image, its own and the next one serve as a text layer: the pips and dice they cite cross-check the reading as in a PDF. An HTML page reads the images of its folder and subfolders, and those written in the page (data:); nothing is downloaded, and online images are counted on the error output. An image drawn as vectors (EMF, WMF, SVG) is not read: it is named on the error output. A Word 97-2003 .doc is refused with a message that suggests saving it as PDF or DOCX.

A PDF none of whose pages is made of images or drawn with this font (a book drawn in vectors) is refused; its pages are then given as images:

Error: document: no diagram drawn with eXtreme Gammon's board font, and no page made of images (a page drawn with vectors is not rendered); give its pages as images: a folder of PNG or JPEG files, one a page; structure: no page of the document could be read: page 1: pdf: the page draws no image (a page drawn with vectors is not rendered)

A PDF drawn with a board font whose shapes are not embedded is refused with a message that names the font.

A file that is neither a PDF, nor a written document, nor an image, an encrypted PDF or one larger than 512 MiB, an image of more than 64 MiB or of more than 100 million pixels is refused too, with a message that says so. A written document has the same 512 MiB limit; its archive is refused beyond 10,000 entries, a part that decompresses to more than 64 MiB or a total decompressed size of more than 1 GiB.

The three-command workflow

./blunderdb document analyze livre.pdf -o releve.json
./blunderdb document check releve.json
./blunderdb document import --db base.db releve.json

  1. analyze reads the PDF and writes the relevé (without -o, it writes it to standard output). When standard error is a terminal, it writes the progress of the reading there (page 37/212, 54 diagrams); nothing is written in a script. It summarises what it found:

    Document:   Mon livre
Entries:    6 (sure 3, to verify 2, uncertain 1)
Context:    read 5, default 0, to verify 1
Positions:  5 distinct, 1 repeated
Relevé:     releve.json

    The title and the author come from the PDF metadata; failing that, the title is the file name; --title and --author replace them. The chapter of each entry comes from the PDF bookmarks.

  2. check validates the relevé and counts its entries, without reading or writing any database. It also lists, after the count, the entries to review (rank, page, state and the fields to compare with the diagram); --format json gives the same counts and the same list (review) in JSON:

    Document:   Mon livre
Entries:    6 (sure 3, to verify 2, uncertain 1; verified 0)
Context:    read 5, default 0, to verify 1
Positions:  5 distinct, 1 repeated
Unverified: rank 4, 5, 6 (import refused without --force)
Review:
  rank 4, p. 12, Problem 3, to-verify: context not read, to check against the diagram: cube (drawn)

    check also accepts the document itself (check livre.pdf): it then reads the relevé that the interface’s verification sheet keeps beside it (livre.pdf.releve.json, The interface’s import assistant) and reports its progress, verified included.

  3. import writes the positions to the collection:

    Created collection "Mon livre" (id 1)
Entries: 6, distinct positions: 5 (5 new in the library), added to the collection: 5, repeated: 1

    --collection chooses a name other than the document title. If the database file does not exist, it is created.

The relevé

The relevé is a readable JSON file that you can open in a text editor. The header (document) gives the title, the author, the edition or the address of the document, the SHA-256 fingerprint of the file read, the profile of its diagrams and, for a scanned book, its default context (defaults, see The default context). Then each diagram is an entry, in the order of the document:

  • rank — its rank, from 1 with no gap;

  • page, chapter and label — its page, the bookmark chapter and the name the document gives it (“Problem 191”) when it is printed above it;

  • position — the position, as an XGID: checkers, cube, side to move, dice, score and match length in a single string;

  • checkers — the certainty of the checkers: sure, to-verify or uncertain;

  • complete — true when the checkers were read at fifteen per side on the board with no doubt, without a cross-check confirming them (see Fifteen and fifteen without a doubt);

  • context — how the context (cube, dice, player on roll, score) is known: read (read and cross-checked), default (the document’s default context), to-verify (neither read nor under the default: a drawn cube or dice that were not read, a score that cannot be found) or uncertain (contradicted);

  • doubts — the named doubts of the reading;

  • rect — where the diagram lies on the page, as a fraction of its size, to find it again in the PDF;

  • verified — true when a person has compared the reading with the diagram.

verify writes a person’s verdict into the relevé, without a database:

./blunderdb document verify releve.json --rank 3,4,9
./blunderdb document verify releve.json --rank 12 --position "XGID=..."
./blunderdb document verify releve.json --rank 12 --undo

--rank names the entries, separated by commas; they become verified. --position replaces the reading of a single entry with the correct XGID, refused if it is not a legal position; a correction whose context is no longer the default’s keeps its own, to verify. --undo removes the verdict. Given instead of the relevé, the document makes the command write into the relevé kept beside it. The command prints the file written and the progress: releve.json: verified 3 of 6 entries (sure 3, to verify 2, uncertain 1).

You review a relevé by opening the PDF at the page of the entry. There you correct the position (the XGID), mark a checked entry with "verified": true, and remove an entry by renumbering the ranks. A relevé is verified over several sessions: verified stays in the file. check refuses a relevé with an unknown field, with a gap in the ranks, with a page that goes backwards, with an XGID that is not a legal position, or of a newer format than the program. sure checkers can carry a doubt only about the context; a read context carries none; a default entry carries the default context in its XGID.

The relevé is in version 2 format. A version 1 relevé, which gave a single state (state) per entry, can still be read: a sure entry there has its checkers sure and its context read, an entry from a scanned book falls under the default context, unconfirmed, and any other has its context to verify. analyze always writes version 2.

The three states

The state of an entry follows from its two certainties; it is not written in the relevé.

sure

The checkers are sure and the context is certified: read, or under the document’s default context once that has been confirmed. The checkers are sure when the cross-checks of the diagram hold: each side has fifteen checkers (on the points, on the bar and in the borne-off tray), and the pips computed from the position equal the pips printed for both players. The context of an XG PDF is read: the score and the match length are those it prints beside it. That of a scanned book never is: see Scanned books.

to-verify

The reading holds, but nothing confirms it: a printed pip differs from the computed pip, or the diagram shows something the reference prints never showed — a stack of more than 9 checkers, numbered checkers on the bar, more than two white or three black checkers on the bar, the cube on the top player’s side or beyond 8, the top player on roll, no mark of the side to move, the black player at the bottom, a Crawford game, a player one point from victory (the Crawford game and the following ones cannot be told apart), font glyphs that the table does not read. These cases are read but never declared sure.

uncertain

The checkers or the context are contradicted, or the reading is incomplete: an unknown glyph, a side that does not count fifteen checkers and whose pips do not match, a damaged frame. A diagram from which no legal position can be drawn keeps its place in the relevé, without a position ("position": "").

An entry is importable when it is sure or verified, or, on request, when it is complete (Fifteen and fifteen without a doubt). The doubts it carries say what to check, for example:

pips read 167/167, printed 160/167 (bottom/top)

The die is not read: the analysis always writes “no dice” (00).

Scanned books

A page image is read with no assumed style: the command looks in it for two rows of twelve points cut by a bar, and for checkers, discs of two classes stacked from the base of a point. It learns the style of the document from the document itself: the shape of the checker on the first diagrams, then, on all of them, the two classes of checkers, the printed numbering and the direction of play. Nothing is kept from one document to the next, and no image is kept.

It reads line-drawn diagrams and printed software screenshots, in reading order: left page then right page of a double page, column, then top to bottom. A slightly skewed page is straightened, the binding shadow erased. Useful resolution: 150 to 300 dpi, the one the file states; failing that, the long side of the page is taken to be eleven inches.

A scanned PDF is read directly, without an external tool: each page is composed of its images, placed as the PDF places them, at the resolution of the finest of them bounded between 150 and 300 dpi, then read and forgotten. Decoded are JPEG images (DCTDecode), JPEG 2000 images (JPXDecode, grey or three components, without a palette, an embedded alpha or HTJ2K, up to 12 million pixels), JBIG2 images (JBIG2Decode, with their JBIG2Globals: generic regions in MMR or arithmetic coding, refinement regions, symbol dictionaries and text regions in arithmetic coding, up to 67 million pixels a page), fax images (CCITTFaxDecode, groups 3 in one dimension and 4) and raw images (FlateDecode, gray, color or indexed); stencil masks and soft masks are applied, so a page made of a JPEG background and fax masks is composed legibly. Not handled are: a color-key mask (the image is painted whole), a JBIG2 image in Huffman coding or in halftones, and a page drawn in vectors (skipped). A page with an image refused by its header is skipped without decoding its other images; an image refused for lack of decoding budget is left out, and the page is read without it if another image paints it. Skipped pages are named on the error output, with their reason; the others are read. The text layer of a page, visible or not (the one an OCR leaves under the image), gives its words their place on the image; a text that its font does not translate into characters gives no word.

On a scanned book, the checkers and the context are certified separately. The checkers are sure when the pips printed beside the diagram equal the computed pips of both sides, when neither side has more than fifteen checkers and when no doubt remains about the checkers. The context is read field by field, and a field counts as read only when cross-checked:

  • the cube, by its value read in its square (the document’s digits) or in the text layer — two sources, when present, must agree — and consistent with its position: 64 in the middle is centered, 2 to 64 at the top or bottom belongs to the player on that side; a lone square with a blank face is the centered cube, when the document draws it so, at the same place, beside at least three diagrams, since an owned cube carries its value;

  • the dice, counted on the image and confirmed by the neighboring text: a named roll (“to play 41”, “rolls a 65”) or a written move in which each step is a die (“2/0 2/1”, “8/5(2) 6/3(2)”), cited twice if the text names several rolls; a word closer to another diagram belongs to that one; the player on roll, by the color of the dice and their half of the board (the right half for the bottom player), which must designate the same player. Without drawn dice, a caption that names them (“Black to play 53”, read from the text layer or, without a text layer, from the image) gives the roll and the player on roll, each in doubt: a single source certifies nothing;

  • the score, by the banner of the text layer (score:, pip:, 7 point match), each score being attributed to the player whose pips it carries; two equal scores do without the pips.

An entry whose whole context is read is "context": "read". A cube that is not found is never taken for centered: whatever is not read takes the document’s default context ("context": "default", with the doubt context not read: cube, dice, player on roll, score). A cube, dice or score drawn or printed but not certified, a context partly read away from the default on a field the document does not print (see The default learned from the document), a cube owned by the top player with no dice drawn, a cube not found in a document that draws it or a score not found in a document that prints it (found beside at least a third of its diagrams) leave the context to verify ("context": "to-verify", with a named doubt); the XGID then carries what was read. An entry from a scanned book whose context is not read is therefore never sure as long as the default context is not confirmed, and one whose context is to verify never is. analyze and check count the entries by context, and separately those whose checkers alone are certified:

Context:    read 0, default 140, to verify 12
Defaults:   centred cube, no dice, the bottom player on roll, money play (0:0:1:00:0:0:0:0:10), not confirmed: set "confirmed": true once the document's diagrams follow them
Checkers:   112 confirmed, their context alone to verify (cube, dice, player on roll, score)

For an entry whose context remains to be verified, open the book at the entry’s page, compare the cube (value and owner: a cube drawn in the middle may be owned), the dice, the player on roll and the score with the diagram, correct these fields of the XGID if needed, then mark "verified": true.

The default context

The default context of a scanned book is the one the reading writes: centered cube, no dice, the bottom player on roll, a free game (no match). It appears in the header of the relevé:

"defaults": {
  "context": "0:0:1:00:0:0:0:0:10",
  "description": "centred cube, no dice, the bottom player on roll, money play",
  "confirmed": false
}

context is the end of the XGID after the board; every default entry carries it. When the document’s diagrams follow this context — a problem book in free play, bottom player on roll, for example — it is confirmed once by writing "confirmed": true: all default entries then have their context certified, and those whose checkers are sure become sure. Only the exceptions the reading has seen (owned cube, drawn dice, match score) and the entries whose checkers are not sure remain to be verified one by one. A context the document does not follow is not confirmed: a cube the reading does not find, a score printed in the image without a text layer or a player on roll given by the prose outside a caption are not seen.

The default learned from the document

The reading learns from the document which context fields it prints beside its diagrams: the cube, the dice (with the player on roll) or the score, read beside at least a third of the diagrams. It names them in printed:

"defaults": {
  "context": "0:0:1:00:0:0:0:0:10",
  "description": "for what a diagram does not print: centred cube, no dice, the bottom player on roll, money play; the document prints its score, read beside each diagram",
  "printed": ["score"],
  "confirmed": false
}

A printed field is the reading of each entry, which the reading has certified; the default context covers only the others. In a match problem book, every diagram carries its score: its entries stay default, each with its score in the XGID, and the single confirmation of the default context certifies the centred cube, the absence of dice and the player on roll of all of them. A diagram whose score is not read in such a document is not taken as money play: its context remains to be verified (the document prints its score beside its diagrams, none is read here: it is not taken as money play). analyze and check display what was learned:

Printed:    score, read beside each diagram (learned from the document)

Nothing is kept from one document to the next. A relevé without printed keeps the strict rule: any field read outside the default leaves the context to be verified.

Fifteen and fifteen without a doubt

A diagram without printed pips has no cross-check: its checkers stay to-verify. Read at fifteen checkers per side with no doubt, they are marked "complete": true: on all the measurements made, these readings were exact, but nothing confirms them diagram by diagram. It is an intermediate state, distinct from sure. Besides the context, a complete entry carries only two doubts: the absence of printed pips, and the assumed direction of play when no pip in the document has confirmed it. Printed pips that differ from the computed pips are a doubt about the checkers: the entry is then never complete. A position from which checkers have been borne off is never complete: when the document draws its bearoff board as bars (a checker borne off seen edge-on), the bars counted in the board, next to the side’s row, bring its drawn checkers up to fifteen, but a stray shape counts there as readily as a checker. That count holds only if printed pips agree with the position, which is then sure; without them, it is a named doubt (counted in the tray, no printed pips confirm them). A board whose bars do not make fifteen is a named doubt (they do not make fifteen).

The assumed direction of play is also a default of the document, with its own confirmation: a wrong direction would swap the players of all the positions read under it. It appears in the default context, under direction:

"direction": {
  "home": "right",
  "description": "direction of play assumed, no printed pips confirm it: checkers move toward the side with the fewer pips, the bottom player's home on the right",
  "confirmed": false
}

Confirming the context does not confirm it. It is checked on a few diagrams, then "confirmed": true is written in direction.

import --accept-complete accepts in bulk the complete entries whose context is certified (read, or under the confirmed default context) and whose direction of play is certain (voted by the pips, or assumed then confirmed), without marking them verified; check counts them, and counts separately those held back by an unconfirmed direction:

Direction:  direction of play assumed, no printed pips confirm it: checkers move toward the side with the fewer pips, the bottom player's home on the right, not confirmed: check it on a few diagrams, then set "direction": {"confirmed": true}
Complete:   84 more held back until the direction of play is confirmed

Complete:   84 with 15 + 15 checkers read with no doubt and a certified context (imported with --accept-complete)
Unverified: rank 3, 7, 12 (import refused without --force; rank 12 with --accept-complete)

The import says how many it accepted (Complete: 84 entries of 15 + 15 checkers read with no doubt). A complete entry whose context is not certified, or whose assumed direction of play is not confirmed, is still refused; the error message says to confirm it.

Printed pips are read from two sources: the text layer of a PDF, and the image itself. In the image, the command reads the isolated numbers around the diagram, on the horizontal band of the board out to about half a board width on each side; a lone letter in front of a number (W 164, B 123) does not prevent it from being read. It reads them digit by digit, by comparison with the document’s point numbering, with eight common embedded fonts, then with the digits already read in the document; a number is returned only if each of its digits is clearly recognised, otherwise it abstains. The location of the pips is learned from the document: a number read that equals the pips of a diagram counted at fifteen checkers per side votes for its place, and two places (top and bottom) must gather enough votes; a place extends over the neighbouring positions that received votes, for a document that places its boards at positions or sizes that vary. No digit is chosen from the pips of the diagram it accompanies, and nothing is kept from one document to the next. When the text and the image each give pips and they differ, the checkers are not confirmed and the doubt says so (the two disagree). An entry without pips read stays to-verify (no printed pip count was found next to the diagram).

A move arrow drawn on the diagram (a straight, thin, oblique line, alone on the paper) is not read as a checker, and the numbers of fifteen or fewer printed beside the board (checker counts, numbers) are not taken for the pips.

Reading the digits assumes dark Arabic digits on a light background, written horizontally, at least 15 pixels high at the reading resolution, pips printed in the same place throughout the document, and about thirty diagrams read at fifteen checkers per side to learn that place.

The doubts name what is left to check: a stack that carries a number, a disc of neither class (a faded or stained checker), a column full from top to bottom, a dark stack counted by its length, a half board (a row without a point), the assumed direction of play (checkers advance toward the side with the fewest pips), borne-off checkers counted by difference, a cube drawn off-center, dice drawn.

Never read: the value and owner of the cube (the default context says it is centered), the dice (none), the score (a free game), the player on roll (the bottom one), the bearoff board when it is not drawn as bars (a side drawn with fewer than fifteen checkers then has the others borne off), checkers drawn as letters (X and O): a document in which no checker is a filled disc is not read, and every diagram is uncertain with this reason (the document draws no filled checker).

Why the import refuses

An entry that is neither sure nor verified is not reliable, and what enters a collection is shared at export. The import therefore refuses the whole relevé, before writing anything, names the ranks and says what to do:

Error: document: entries neither sure nor verified: storage: invalid argument: rank 4, 5, 6; check the cube, dice, player on roll and score of an entry whose context is not certified against its diagram; verify the others ("verified": true), or force the import

When entries are under an unconfirmed default context, or complete without --accept-complete, the message says so too:

Error: document: entries neither sure nor verified: storage: invalid argument: rank 1, 2; confirm the document's defaults once if its diagrams follow them ("defaults": {"confirmed": true}); accept the entries of fifteen checkers a side read with no doubt as a whole (accept complete); check the cube, dice, player on roll and score of an entry whose context is not certified against its diagram; verify the others ("verified": true), or force the import

You verify these entries, or pass --force to import the relevé as it is; the import then says how many entries it forced (Forced: 3 entries neither sure nor verified).

The fallback

An entry whose checkers are certified (sure, or complete with --accept-complete and a certain direction of play) and whose only remaining issue is the context to be verified is not necessarily rejected: once the default context is confirmed, the import offers to fall back on the context its XGID carries, which is what was read and the default for the rest. check names these ranks, and the error message offers the fallback:

Fallback:   rank 4 imported with --fallback under the context its position carries, the fields to check named in its reference

import --fallback imports these entries without marking them verified; the reference of each, in its comment, names the fields to check against the diagram with the doubt the reading left there, contradiction included (p. 12, Problem 31 (context not read, to check against the diagram: cube (cube drawn, value not read))), and the import counts them (Fallback: 1 entries under the context their position carries). The fallback covers neither an entry whose checkers are to be verified, nor a contradictory context, nor an unconfirmed default context. Even with --force, an entry without a position is refused: it must be filled in or removed.

What enters the database

Only the positions enter, in the order of the document, in a collection named after the document (or after --collection). Each position enters as a position brought on its own, and the library recognises it by its identity: a position it already has is not duplicated (new in the library counts those it lacked).

  • The description of the collection carries the title, the author, the edition and the address of the document, one per line. An existing collection of the same name receives the positions it lacks and keeps its description if it has one; a dynamic collection (defined by a query) is refused.

  • Each position carries a comment that gives its reference, after the document title: Mon livre — p. 146, Problem 191.

Nothing else ever enters: no image, no rectangle, no text of the author. An interrupted or refused import writes nothing: it is a single transaction.

A repeated position

When the document shows the same position twice, it enters the collection only once, at its first appearance. Its comment cites each reference: Mon livre — p. 2, Problem 1; p. 4. repeated counts these repetitions.

Re-importing

Re-importing the same relevé adds nothing: no new position, nothing in the collection (added to the collection: 0), and the reference comment is rewritten only if its references changed, never doubled. You can therefore resume an import after correcting the relevé.

The daemon

The serve daemon imports a relevé under /v1/documents.importReleve with the same rules; it analyses no document (see Headless mode (server)).

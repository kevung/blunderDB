9. Roadmap

This page lists the ideas under consideration for blunderDB — it is not a commitment on dates or order. blunderDB is developed by one person, in spare time: an idea can move fast, wait for months, or be dropped if a better one replaces it.

Precise tracking happens on GitHub:

  • open tickets are grouped by stage in the milestones Étape 3 — Étendre (what follows on this page) and Étape 4 — Fond (the heavier undertakings);

  • to suggest or discuss an idea, head to the Discussions — Ideas category;

  • every published release is announced in the Discussions — Announcements category.

10. Stage 3 — Extend

10.1. Import and flow

  • An end-of-import panel: number of matches imported, marked positions, positions with no analysis, five worst errors (#257).

  • Watch a folder (eXtreme Gammon’s, for instance) and automatically import every new file (#258).

  • After an import, work through a study queue showing only the batch’s blunders, marked positions and close decisions (#259).

  • Import matches played on bgammon.org, and recognise an OGID position identifier pasted into the application (#262).

  • Keep track of where each comment came from (user, eXtreme Gammon, GNUbg…) and show all of them, instead of one picked at random (#263).

10.2. Categorising without imposing a taxonomy

  • Automatically tag every position with the phase of the game (opening, middle game, race, bearoff), so it can be filtered and found in the statistics (#264).

  • A suggested tag vocabulary (#blitz, #backgame, #containment…) with autocomplete, and a panel listing them by frequency (#265).

  • A fifth statistics tab breaking down PR and error rate by phase, by tag and by away score, as a matrix (#266).

10.3. Analysis and evaluation

  • For the current position, the cube verdict at every score of a 5-, 7- or 9-point match, in a single grid (#267).

  • A PR computed on matches with no imported analysis, by comparing the move played to the built-in evaluator’s recommendation (#268).

  • Compare, side by side on the same position, what the different engines already present in the database say (#269).

  • Publish how good the built-in evaluator really is against an exact reference table, and measure it continuously against eXtreme Gammon imports (#270).

  • Show the rules in force (cube limit, Jacoby, beaver) next to the verdict, and allow choosing the match-equity table per database (#271).

  • Publish a measurement of 3-ply (time, accuracy gain) and expose it as a setting if the trade-off justifies it (#272).

10.4. Learning

  • A first timed training module: pip count, EPC, take point (#273).

  • Set a progress goal (“PR under 5 within three months”) and track the gap on the curve (#274).

  • Connect study statistics (Anki) to real-game statistics: does a reviewed category actually improve (#275)?

  • Chained cube cards: double, then take, as two separate questions rather than a single two-step card (#276).

  • Learning paths: an ordered sequence of annotated positions, distributable as a watermarked database, designed for a coach (#277).

10.5. Sharing an analysis

  • A single board rendering, exportable as SVG or PNG, faithful to what the screen shows (#278).

  • A standalone HTML report for a session, a match or a tournament, printable to PDF from the browser (#279).

  • Export to CSV or Parquet, with a sample Jupyter notebook kept up to date (#280).

  • An index, on this site, of watermarked databases that other players share with a verifiable identity (#281).

10.6. Search and library

  • Collections that re-evaluate themselves on open (a named filter, never frozen), and comparing two players side by side in the Players tab (#282).

  • Write a search in plain language (“my cube blunders at the score”) instead of tokens, deterministically and offline (#283).

10.7. Interface and platform

  • A welcome screen that offers, when no recent database is open: guided tour, sample database, import my matches, open a database (#284).

  • A trash for deleted positions, and an “undo” on the most common deletions (#285).

  • Named themes — light, dark, high contrast, printable (#286).

  • A series of small everyday conveniences: a browsable activity log, a command palette, more readable search badges (#287).

  • State plainly what works to synchronise a database across several machines (and what doesn’t), and a button to merge two databases (#288).

  • A minimal client and a versioning policy for the server mode’s API (#289).

  • Bring into the application capabilities that today only exist server-side: suspending a card, a review log, FSRS optimisation (#290).

11. Stage 4 — Foundational undertakings

These ideas change the nature of part of the software; each awaits an explicit decision before being started.

  • Automatically classify a position’s type of game (race, holding, backgame, blitz…), name recurring error themes (too passive, timing, underestimated gammon…), and group repeating blunders by cumulative cost — the promise the product’s name makes (#291).

  • Truncated rollouts to settle between two very close moves, with a displayed confidence interval (#292).

  • “Positions like this one”: finding the positions closest to the one on screen (#293).

  • A quiz mode that tests rather than memorises, with a training PR comparable to the real PR (#294).

  • A read-only web interface on top of server mode, for tablet and mobile (#295).

  • A club or coach mode on the server: sharing a library read-only, receiving students’ matches (#296).

  • A distilled evaluation network, much faster, and an evaluation cache that survives the application closing (#297).

  • Explaining a blunder in one sentence, without resorting to a language model (#298).

  • An optional assistant, strictly local and never enabled by default, via Ollama (#299).

12. What is not planned

Playing against the built-in evaluator would change the nature of the product (a full game engine: rules, input, game history); it is not on blunderDB’s agenda (#300).

9. ロードマップ

このページは blunderDB について検討中の発展の方向性を挙げたものであり、時期や順序を約束するものではありません。blunderDB は一人の開発者が余暇に開発しています。ある方向性が急速に進むことも、何か月も止まることも、より良い案に取って代わられて放棄されることもあります。

詳細な進捗は GitHub で管理しています。

  • 未解決のチケットは、マイルストーン 第 3 段階 — 拡張 (このページに続くもの) と 第 4 段階 — 基盤 (より重い作業) に段階別にまとめられています。

  • アイデアの提案や議論は Discussions — Ideas カテゴリ へどうぞ。

  • 公開された各バージョンは Discussions — Announcements カテゴリ で告知されます。

10. 第 3 段階 — 拡張

10.1. インポートと作業の流れ

  • インポート完了パネル: インポートした試合数、マークした局面、解析のない局面、最悪の 5 つのミス (#257)。

  • フォルダー (たとえば eXtreme Gammon のもの) を監視し、新しいファイルを自動的にインポートする (#258)。

  • インポート後、その一括分のブランダー、マークした局面、際どい判断だけを表示する学習キューをたどる (#259)。

  • bgammon.org でプレイした試合をインポートし、アプリケーションに貼り付けられた OGID 局面識別子を認識する (#262)。

  • 各コメントの出所 (ユーザー、eXtreme Gammon、GNUbg など) を記録し、無作為に選ばれた 1 つではなくすべてを表示する (#263)。

10.2. 分類を押しつけずに分類する

  • 各局面をゲームの局面 (序盤、中盤、競走、ベアオフ) に応じて自動的にラベル付けし、絞り込みや統計から見つけられるようにする (#264)。

  • 補完付きの推奨タグ語彙 (#blitz、#backgame、#containment など) と、頻度順に一覧するパネル (#265)。

  • 局面別、タグ別、アウェイスコア別に PR とエラー率を行列の形で分解する 5 つ目の統計タブ (#266)。

10.3. 解析と評価

  • 現在の局面について、5 点、7 点、9 点マッチのあらゆるスコアでのダブルの判定を 1 つの表にまとめる (#267)。

  • 解析が付いていない試合について、指された手を内蔵評価器の推奨と比べて PR を算出する (#268)。

  • 同じ局面について、データベースにすでにある複数のエンジンの見解を並べて比較する (#269)。

  • 内蔵評価器が厳密な参照表に対してどれだけ正確かを公表し、eXtreme Gammon のインポートに対して継続的に測定する (#270)。

  • 適用中のルール (最大キューブ、ジャコビー、ビーバー) を判定の横に表示し、データベースごとにマッチエクイティ表を選べるようにする (#271)。

  • 3-ply の測定 (所要時間、精度の向上) を公表し、割に合うなら設定として公開する (#272)。

10.4. 学習

  • 時間を計る最初の訓練モジュール: ピップ数、EPC、テイクポイント (#273)。

  • 上達の目標 (「3 か月で PR を 5 未満に」) を立て、曲線上でその差を追う (#274)。

  • 学習の統計 (Anki) を実戦の統計に結び付ける。復習した分類は本当に良くなっているか (#275)。

  • 連鎖するキューブカード: ダブル、次にテイクを、2 段構えの 1 枚ではなく別々の 2 問として扱う (#276)。

  • 学習コース: 注釈付きの局面を順に並べたもので、透かし入りデータベースとして配布でき、コーチのために考えられたもの (#277)。

10.5. 解析を共有する

  • 画面に見えるとおりの、SVG または PNG に書き出せる単一の盤面描画 (#278)。

  • セッション、試合、トーナメントの自己完結した HTML レポート。ブラウザーで PDF に印刷できる (#279)。

  • CSV または Parquet への書き出しと、保守された Jupyter ノートブックの例 (#280)。

  • 検証可能な身元とともに他のプレイヤーが共有する透かし入りデータベースの、このサイト上での目録 (#281)。

10.6. 検索とライブラリ

  • 開くたびに評価し直されるコレクション (固定されない、名前付きの絞り込み) と、プレイヤータブでの 2 人の並列比較 (#282)。

  • トークンではなく日常の言葉で検索を書く (「スコア時のキューブのブランダー」)。決定的で、オフラインで動作する (#283)。

10.7. インターフェースとプラットフォーム

  • 最近開いたデータベースがないときに、ガイドツアー、サンプルデータベース、自分の試合のインポート、データベースを開く、を提示するホーム画面 (#284)。

  • 削除した局面のためのごみ箱と、もっとも多い削除操作に対する「元に戻す」 (#285)。

  • 名前の付いたテーマ — 明るい、暗い、高コントラスト、印刷向け (#286)。

  • 日々の使い勝手を高める小さな改良の数々: 閲覧できる操作履歴、コマンドパレット、より読みやすい検索バッジ (#287)。

  • 複数の端末でデータベースを同期するために何が有効で何が有効でないかを明言することと、2 つのデータベースを統合するボタン (#288)。

  • サーバーモードの API のための最小限のクライアントとバージョン方針 (#289)。

  • 今日はサーバー側にしかない機能をアプリケーションに引き上げる: カードの保留、復習履歴、FSRS の最適化 (#290)。

11. 第 4 段階 — 基盤となる作業

これらの方向性はソフトウェアの一部の性質を変えるものです。着手の前にそれぞれ明示的な決定を必要とします。

  • 局面の戦型 (競走、ホールディング、バックゲーム、ブリッツなど) を自動的に分類し、繰り返し現れるミスの主題 (受け身すぎる、タイミング、ギャモンの過小評価など) に名前を与え、繰り返されるブランダーを累積コストでまとめる — 製品名が約束するもの (#291)。

  • ごく近い 2 手を分けるための切り詰めたロールアウト。信頼区間を表示する (#292)。

  • 「これに似た局面」: 画面の局面にもっとも近いものを見つける (#293)。

  • 暗記ではなく試すクイズモード。実戦の PR と比較できる訓練用 PR を伴う (#294)。

  • タブレットと携帯のための、サーバーモード上の閲覧専用ウェブインターフェース (#295)。

  • サーバー上のクラブ / コーチモード: ライブラリを読み取り専用で共有し、生徒の試合を受け取る (#296)。

  • はるかに高速な蒸留された評価ネットワークと、アプリケーションを閉じても残る評価キャッシュ (#297)。

  • 言語モデルに頼らずに、ブランダーを一文で説明する (#298)。

  • 厳密にローカルで、既定では決して有効にならない任意のアシスタント。Ollama を利用する (#299)。

12. 予定にないこと

内蔵評価器と対戦することは製品の性質を変えてしまいます (ルール、入力、対局履歴を備えた完全なゲームエンジンになる)。blunderDB の予定には入っていません (#300)。

データベースの管理

info — データベースのメタデータ

データベースのメタデータと統計を表示します。

./blunderdb info --db <path> [--format <format>] [--estimate]

オプション：

  • --db — データベース（必須）。

  • --format — 出力フォーマット：text または json（デフォルト：text）。

  • --estimate — 非常に大きなデータベースで即座に応答します。200 000 行を超えると数値は推定値（上限）となり、JSON では approximate に列挙され、テキストでは「≈」が付きます。ブランダーはキャッシュされた件数がまだ有効な場合にのみ示されます（そうでなければ blunder_count はありません）。既定ではすべての行を数えます。ブランダー数はデータベース内にキャッシュされ、それを変えうる書き込み（インポート、解析、削除、しきい値の変更）の後に数え直されます。

例：

./blunderdb info --db base.db

# Database Information
# ==================================================
# Path: /home/jean/bg/base.db
#
# Metadata:
#   Version: 2.31.0
#   User: Jean
#   Description: Matchs de tournoi 2025
#   Date of Creation: 2026-09-06 02:43:51
#
# Statistics:
#   Positions: 3859
#   Analyses: 3855
#   Matches: 11
#   Games: 61
#   Moves: 3766
#   Blunders: 142
#
# Thresholds (millipoints):
#   Error: 50
#   Blunder: 100

--format json はファイルの出所を加えます——issuance には、透かしがあればその透かしと、このマシンの発行者アイデンティティが入ります：

./blunderdb info --db base.db --format json

{
  "issuance": {
    "watermarked": false,
    "issuerFingerprint": "1186-57FA-060C-9378",
    "issuerName": "unger"
  },
  "library_settings": {
    "errorThresholdMP": 50,
    "blunderThresholdMP": 100
  },
  "metadata": {
    "database_version": "2.31.0",
    "dateOfCreation": "2026-09-06 02:43:51",
    "description": "Matchs de tournoi 2025",
    "user": "Jean"
  },
  "path": "/home/jean/bg/base.db",
  "stats": {
    "analysis_count": 3855,
    "blunder_count": 142,
    "game_count": 61,
    "match_count": 11,
    "move_count": 3766,
    "position_count": 3859
  }
}

edit — メタデータを編集する

データベースのユーザー名、説明、または閾値を編集します。

./blunderdb edit --db <path> [options]

オプション：

  • --db — データベース（必須）。

  • --user — 新しいユーザー名。

  • --description — 新しい説明。

  • --clear-user — ユーザー名を削除する。

  • --clear-description — 説明を削除する。

  • --error-threshold — エラーの閾値（ミリポイント単位）。この値以上の損失となる決定はエラーです。

  • --blunder-threshold — ブランダーの閾値（ミリポイント単位）。この値以上の損失となるエラーはブランダーです。

  • --format — 出力フォーマット：text（デフォルト）またはjson（{"changes": [...]}）。

少なくとも1つの編集オプションが必要です。

例：

./blunderdb edit --db base.db --user "Marie" --description "Ma collection"
./blunderdb edit --db base.db --clear-description
./blunderdb edit --db base.db --error-threshold 20 --blunder-threshold 80

verify — 整合性を確認する

データベースの整合性を確認し、オプションでマッチとそのソースファイルを比較します。

./blunderdb verify --db <path> [--match <id>] [--mat <file.mat>]

オプション：

  • --db — データベース（必須）。

  • --match — 確認するマッチのID。

  • --mat — 比較するMATファイル（--match と共に使用）。

  • --format — 出力フォーマット：text（デフォルト）またはjson（統計、孤立行、スキーマの差分、および該当する場合はマッチの検証）。

--match オプションなしの場合、コマンドはデータベースの一般統計を表示します。--match を使用すると、マッチのデータを確認し、元のソースファイルと比較できます。

各実行では参照整合性も検査します。孤立した行——マッチのないゲーム、ゲームのない手、手のない手の解析、ポジションのない解析、デッキまたはポジションのない復習ジャーナルの項目、セッションのないトレーニングの問題——を数え、存在すれば合計とともに WARNING 行を表示します。健全なデータベースは Orphaned rows: none と答えます。すべての接続で外部キーを強制していなかったバージョンが書いたデータベース、あるいは復習ジャーナルが自分の外部キーを持つ前のデータベースには、孤立行が残っていることがあります。どのマッチにもどのデッキにも属さず、場所を取るだけです。それでもコマンドの終了コードは 0 のままです。

各実行では、スキーマを参照 DDL と比較し、データベースに欠けているテーブル・列・インデックスを一覧します。データベースを開くときには、可能であれば欠けているものが追加され、追加できないもの（典型的には重複行のせいで再構築できないUNIQUEインデックス）はログに記録されるだけです。このずれが目に見えるのはここであり、これらの要素を名指しするクエリは原因が修正されるまで失敗します。健全なデータベースはSchema: matches the reference DDLと答えます。孤立行と同じく、スキーマのずれは所見であって失敗ではなく、終了コードは 0 のままです。

各実行では最後に、現在の DDL が定めているものの SQLite が既存のテーブルに追加できない規則を検査します。すなわち範囲のCHECK制約（サイコロは 0 から 6、キューブとピップは非負、上がった駒は 0 から 15、復習の評価は 1 から 4）、行に決して欠けてはならない Zobrist ハッシュ、そして 1 つの局面につき 1 つの解析という一意性です。スキーマ 2.18.0 以降に作成されたデータベースはこれらを強制します。それより古いデータベースには、新しいデータベースなら拒否する行が残っていることがあり、ここで規則ごとに数えられるのはそれらです。健全なデータベースはConstraints: every row satisfies the current DDLと答えます。これもまた所見にすぎません。何も修復されず、終了コードは 0 のままです。

各実行では最後に、非正規化された 2 つのカウンタmatch.game_countとgame.move_countを、それらが数えていると称する行から再計算し、いくつが食い違っているか、最悪でどれだけ違うかを報告します。どちらもインポート時に一度だけ、ソースファイルの内容から書かれ、マッチ一覧と対局ビューが表示するのはこの値です。小さなずれはたいてい、変換できなかったものを飛ばしたインポートです。何も書き換えられません——カウンタを保存済みの値で置き換えれば、まさに見るべきずれが消えてしまいます。健全なデータベースはCounters: game_count and move_count agree with the rowsと答えます。

例：

./blunderdb verify --db base.db
./blunderdb verify --db base.db --match 1
./blunderdb verify --db base.db --match 1 --mat original.mat

これを門番として使う。コマンドが何を見つけても終了コードは 0 です。判定を運ぶのは --format json であり、スクリプトは自分でカウンターを読む必要があります。

{
  "stats": {
    "analysis_count": 3855,
    "blunder_count": 142,
    "game_count": 61,
    "match_count": 11,
    "move_count": 3766,
    "position_count": 3859
  },
  "orphans": {
    "games_without_match": 0,
    "moves_without_game": 0,
    "move_analyses_without_move": 0,
    "analyses_without_position": 0,
    "reviews_without_deck": 0,
    "reviews_without_position": 0,
    "training_items_without_session": 0
  },
  "orphan_total": 0,
  "schema_drift": {
    "missing_tables": null,
    "missing_columns": null,
    "missing_indexes": null
  },
  "schema_drift_count": 0,
  "constraint_violations": [
    {"name": "position.zobrist_hash NOT NULL", "count": 0},
    {"name": "position.dice_1 BETWEEN 0 AND 6", "count": 0}
  ],
  "constraint_violation_total": 0,
  "counter_drift": {
    "matches_with_wrong_game_count": 0,
    "games_with_wrong_move_count": 53,
    "worst_game_count_gap": 0,
    "worst_move_count_gap": 2
  },
  "counter_drift_total": 53
}

警戒すべき項目は3つです。orphan_total、schema_drift_count、constraint_violation_total です。ゼロでなければ、修復が必要なデータベースであることを表しています。

./blunderdb verify --db base.db --format json \
  | jq -e '.orphan_total == 0 and .schema_drift_count == 0 and .constraint_violation_total == 0'

counter_drift_total はそこに含まれません。上の例がそれを示しています。この出力を生んだデータベースはインポートされたばかりですが、手のカウンターが行の内容と食い違うゲームがすでに 53 件あります。これらのカウンターは元のファイルに由来するもので、データベースに由来するものではありません。差はインポートの事情を語るのであって、破損を知らせるものではありません。目を通すのはよいですが、しきい値としては使わないでください。

vacuum — データベースを最適化する

削除（マッチ、トーナメント、パージ）によって空いたディスク領域を回収します。SQLite はデータを削除してもファイルを自分で縮めることはなく、明示的に指示する必要があります。最適化を起こす方法はこれだけです。大きなデータベースでは費用が読めないため、データベースを開いたときに自動で行われることはありません。

./blunderdb vacuum --db <path>

オプション：

  • --db — データベース（必須）。

  • --format — 出力フォーマット：text（デフォルト）またはjson（バイト単位の{"size_before", "size_after", "reclaimed"}）。

このコマンドはまず wal_checkpoint(TRUNCATE) を実行し、最適化前に表示されるサイズが正直な値になるようにします。次にファイルの隣にファイルのおよそ1倍のサイズの空き容量があることを確認し、最適化したデータベースをコピー（VACUUM INTO）に書き込んでからファイルと置き換え、続いてクエリプランナが使う統計を更新するために ANALYZE を実行します。別のプログラムがデータベースを開いている場合、ファイルは置き換えられず、コマンドはその場で最適化（VACUUM）します。このときはファイルサイズのおよそ2倍の空き容量が必要です。ディスク容量が足りない場合は、中断された最適化の危険を冒すのではなく、明確なメッセージとともに開始を拒みます。

最適化の前に、以前のバージョンが JSON のまま保存していた分析はすべて、コンパクトなバイナリ形式で書き直されます（reencodeを参照）。

例：

./blunderdb vacuum --db base.db

# Compacting database...
#   Before: 128.4 MiB
#   After:  41.2 MiB
#   Reclaimed: 87.2 MiB

met — データベースのマッチエクイティテーブル

gammonNet がデータベースのマッチスコアの評価に使うマッチエクイティテーブル（MET）を、一覧表示、読み込み、または選択します。既定は内蔵の Kazaross-XG2 で、GNUbg の .xml 形式の明示的なテーブルも使えます。計算された各解析はそのテーブルを記録します。現在のテーブルと異なるテーブルで計算されたマッチスコアの解析は、統計から除外されます。テーブルを変更しても解析は書き換えられません。

./blunderdb met --db <path> [--import <fichier.xml> [--current] | --use <id>]

オプション：

  • --db — データベース（必須）。

  • --import — GNUbg の .xml テーブルを読み込みます。すでに存在するテーブル、または Kazaross-XG2 と同一のテーブルは、重複して追加されません。

  • --current — --import と併用：読み込んだテーブルを現在のテーブルにします。

  • --use — 指定した識別子のテーブルを現在のテーブルにします。0 で Kazaross-XG2 に戻ります。

  • --format — 出力フォーマット：text（デフォルト）またはjson。

その後、コマンドはデータベースのテーブルを表示し、現在のテーブルには * が付きます。デーモンは同じ操作を met.list、met.import、met.setCurrent、met.ofAnalysis の各ルートで公開し、呼び出し元のテナントに限定されます。

例：

./blunderdb met --db base.db --import Rockwell-Kazaross.xml --current

#     0  Kazaross-XG2
# *   1  Rockwell/Kazaross 25 point MET

reencode — 分析をコンパクトな形式で書き直す

分析はコンパクトなバイナリ形式で保存されます。サイズは以前のバージョンの圧縮 JSON の約半分で、読み直しは数倍高速です。この形式より前に作成されたデータベースもそのまま読み込めます。古い分析は、書き直されるとき（分析を補完するインポートやvacuum）に変換されます。reencodeはファイルを圧縮せずにそれらをすべて変換します。vacuumが書き込む最適化済みコピーの置き場がディスクにない場合や、vacuumを持たない PostgreSQL サーバーで有用です。

./blunderdb reencode --db <path>

オプション：

  • --db — データベース（必須）。

  • --format — 出力フォーマット：text（デフォルト）またはjson（書き直した分析の件数を表す{"rewritten"}）。

変換は 2 000 件ずつのバッチで進み、各バッチは独自のトランザクションで実行されます。中断された場合、次回の起動時に停止した位置から再開します。すでに変換された分析は再読み込みせずにスキップされます。読み込めない分析はそのまま残され、ログに記録されます。自動的に起動することはありません。デーモンは同じ操作をルートmaintenance.reencodeで公開し、呼び出し元のテナントに限定されます。

例：

./blunderdb reencode --db base.db

#   Analyses rewritten: 15623468

maintenance — データベースの健全性

メンテナンス操作ごとに 1 行：何を数えるか、そのアクション、最新の実行。何も自動的には起動しません。データベースを開くときも、状態を読むときも同様です。

./blunderdb maintenance status --db <path>
./blunderdb maintenance count <opération> --db <path>
./blunderdb maintenance ids <opération> --db <path>
./blunderdb maintenance run <opération> --db <path>

サブコマンド：

  • status — すべての操作を、無料のカウンタと各操作の最新の実行とともに表示します。コストの高いカウンタは (count on demand) と表示され、count が計算します。

  • count — 操作のカウンタを、コストにかかわらず計算します。

  • ids — 操作が数える識別子（ポジションまたはマッチ）を一覧表示します。その数が count の答えです。

  • run — 操作のアクションを実行し、最新の実行として記録します（完了、キャンセル、失敗）。Ctrl-C で 2 つのバッチの間に停止します。

オプション：

最新の実行は設定とともにデータベースに保存されます。エクスポートには含まれません。同時に実行される操作は 1 つだけです。デーモンは同じサブコマンドをルート maintenance.status、maintenance.count、maintenance.ids、maintenance.run（NDJSON ストリーム、maintenance.cancelでキャンセル可能）で公開し、呼び出し元のテナントに限定されます。そのテナントで gammonNet 分析またはロールアウトが実行中に要求された操作は拒否されます。

例：

players — プレイヤー名の表記

同じ人物が、ファイルごとに異なる表記で署名することがあります（「Doe J.」「John Doe」）。別名は、ある名前が正規の名前の別の表記であることを示します。すでにデータベースにあるマッチは、ファイルに書かれた名前をそのまま保ちます。統計、プレイヤーの表、検索 pl"…" はすべての表記を一人の人物として読み、以降のインポートは正規の名前を記録します。マッチウィンドウのプレイヤー統合も同じ別名を作ります。

./blunderdb players alias <add|list|remove|suggest> --db <chemin> [arguments]

アクション：

  • add ALIAS CANONIQUE — ALIAS が CANONIQUE の表記になります。それ自体が別名である正規名は、その正規名までたどられ、ALIAS を指していた別名は CANONIQUE に移ります。階層は一つだけで、連鎖は作りません。

  • list [--format text|json] — 別名を正規名ごとに並べて表示します。

  • remove ALIAS — 別名を忘れます。別名でなかった場合はエラーで終了します。

  • suggest [--format text|json] — 大文字小文字、アクセント、句読点、語順だけが異なる名前を、最も頻度の高い表記を正規名として提案します。何も記録されません。各提案は、それを適用する add コマンドの形で書かれます。

フィンガープリント。 マッチのフィンガープリント（match_hash、canonical_hash）はファイルの名前を保ちます。別名はその後に、記録された名前にだけ適用されます。別名が存在する前にインポートされたファイルは、そのため次のインポートでも常に認識されます。別の表記でインポートされたマッチで、ダイスがデータベース内のマッチと同じであり、名前が既知の別名だけで異なる場合は、同じマッチとして認識されます。その解析は既存のマッチを補強し、二つ目のマッチは作られません。

./blunderdb players alias add --db base.db "Doe J." "John Doe"
./blunderdb players alias suggest --db base.db

players merge — マッチウィンドウのプレイヤー統合です。デーモンのルート matches.mergePlayersと同じコードで動作し、各名前が正規の名前の表記になります。players alias add を同じ数だけ実行した場合と同じです。

./blunderdb players merge --db <chemin> --into <CANONIQUE> <NOM> [<NOM>...]

players swap — ファイルが誤った順序で名付けていたマッチの 2 人のプレイヤーを入れ替えます(ルート matches.swapPlayers)。ポジションも解析も変わりません。各プレイヤーは自分の統計を、もう一方の席で保ちます。マッチに書き起こしの下書きが開いている間、および blunderDB で対局したマッチでは、入れ替えは拒否されます。

./blunderdb players swap --db <chemin> <ID_MATCH>

players main — マッチウィンドウのメインプレイヤー（ルート players.main.*）。名前なしではメインプレイヤーを表示し、名前ありではそのプレイヤーを指定して、本人またはその別名のいずれかが2番手であるすべてのマッチを一つのトランザクションで入れ替えます。以降のインポートは、そのプレイヤーを1番手に置きます。--dry-run は何も変更せずに入れ替え対象のマッチを表示し、--clear は何も戻さずにメインプレイヤーを解除します。書き起こしの下書きが開いているマッチや blunderDB で対戦したマッチはそのままにされ、別に一覧表示されます。

./blunderdb players main --db <chemin> [--dry-run] [<NOM>]
./blunderdb players main --db <chemin> --clear

players matches — プレイヤーのマッチの識別子。どちらの席でも、すべての別名を通じて取得します（ルート players.matchIds）。

./blunderdb players matches --db <chemin> <NOM>

./blunderdb players merge --db base.db --into "John Doe" "Doe J." "J. Doe"
./blunderdb players swap --db base.db 42
./blunderdb players main --db base.db --dry-run "John Doe"

events — イベント名の表記

players alias と同じアクションを、イベント名（ファイルの Event フィールド）に対して行います。インポート時、イベントが別名であるマッチは、正規名のトーナメントに入ります。

./blunderdb events alias add --db base.db "Open 2025" "Open d'automne 2025"
./blunderdb events alias list --db base.db

repair — 導かれたものを再計算する

データベースが保存内容から導くものを再計算します。各分析の scalar 列を、その分析自体から。各局面の局面フェーズと戦型を、その盤面から。そして各スコアの Crawford 標識を、その局面が由来する対戦、またはその局面が持ち込まれた XGID から。分析そのものには手を触れません。作り直されるのは、そこから導かれていた値です。

このバージョンより前のバージョンで別のデータベースのインポート（import --type database、監視対象の同期フォルダー経由も含む）により解析を受け取ったデータベースは、それらの解析を列なしで、または置き換えた解析の列のまま保持しています。その blunder は数えられず、強制手は判断として扱われます。repair はこれらの列を保存された解析から得られる値と比較し、異なるものを作り直します。同じ内容は transfer で取り込んだ場合と同じように数えられます。

./blunderdb repair --db <path>

オプション：

  • --db — データベース（必須）。

  • --format — 出力フォーマット：\ text\ （デフォルト）または\ json\ 。パスごとに 1 つのカウンター：\ repaired\ （分析列）、\ phases\ （再分類された局面）、\ crawford\ （ハッシュを再計算した局面）、signatures_unverified（再ハッシュによって未検証のままになる署名付きコメント。署名はポジションの識別情報を対象とします）。それぞれが実際に変更された行数を示します。\ --stats\ を付けると、\ match_stats\ （再計算されたマッチ）が加わります。 --move-errors を付けると move_errors(評価した手の数)が加わります。

  • --stats — マッチごとの統計もゼロから再計算します。

  • --move-errors — 指した各手について、その局面の解析から読み取った、最善手に対して失ったエクイティも書き込みます(手テーブルの error_mp 列)。この処理は再開可能で、中断しても止まった所から再開します。非常に大きなライブラリでは数分かかります。サーバー側:matches.scoreMoves。

  • --duplicatesー どの処理も実行せず、ダイスが同一であるマッチのペアを、何も統合せずに一覧表示します(下記参照)。

マッチごとの統計とは、各マッチの各プレイヤーについて、その判断、累積エラー、PR、ブランダー、運、そして分析の主な出所です。統計は、すべての判断をたどり直す代わりにこれらを読みます。統計はインポート時にマッチとともに書き込まれ、それを変える変更（マッチの削除、プレイヤーの入れ替え、そのマッチの局面の分析の変更、ブランダーしきい値の変更）のたびに消去されます。次の読み取りで足りない分が再計算されます。以前のバージョンから移行したデータベースは、最初に開いたときに一度だけ計算します。--statsはそのすべてをやり直します。この集計が万一誤った場合の手段です。

重複の可能性があるマッチ。 repair --duplicatesは、マッチを名前ではなく常にダイスで比較します。2つのケースが報告されます。プレイヤー名が異なるだけで、長さ、初期スコア、各ゲームのダイスが同一であるマッチと、ダイスが別のマッチのダイスを延長しているマッチ(途中で切れた後に完成したマッチ)です。ダイスが同一のペアの下に、テキスト出力は、2つのマッチに同じプレイヤーを名指しさせるplayers alias addコマンドを示します。両方に共通の名前が1つある場合は読みが1つだけ(もう一方の名前はもう一人のプレイヤーでしかありえません)、そうでなければ2つ(席ごと、次に交差)で、番号が付けられ、実行するのはそのうち1つだけです。より新しいマッチの表記が別名に、より古いマッチの表記が正規名になります。--format jsonは {"suspects": [...]} を返し、各ペアに kind(same_dice または longer)、matchId、otherId、players、otherPlayers、さらにダイスが同一のペアではpairings（読みの一覧。各読みにaliases（alias、canonical）が付きます）が含まれます。ダイスのフィンガープリントが存在する前にインポートされたマッチは、その際にフィンガープリントを受け取ります。これがこのモードで唯一の書き込みです。

取り込んだ解析の読み方を修正したあとに役立ちます。これはすでに二度起きています。XG の取り込みは「ダブルしない」を二通りに書き、その二つめが本物のダブルとして解釈されていました。列は起こらなかったダブルの誤差を持っていたのです。また blunderDB 自身が計算した解析はどの手が指されたかを知らず、解析なしで取り込んだマッチはどこも誤差ゼロのまま PR 0,00 になっていました。この列はマッチの手から計算し直されます。読み方を直しても、すでに書かれた行は変わりません。このコマンドがそれを作り直します。

Crawford のパスだけは、局面そのものに手を入れます。スコアの1は「あと 1 点、そしてこの試合が Crawford である」を、0は「あと 1 点、Crawford はもう終わっている」を意味します。インポータがこの区別を書かなかった間、Crawford 後の局面はすべて Crawford の局面として保存され、したがってダブリングキューブが死んだものとして読まれていました。実際には、負けている側が最初の機会にダブルする場面です。スコアを直すと局面のハッシュが変わります。つまりその行はハッシュを取り直され、正しい双子がすでにデータベースにあればそれと統合されます。分析、コメント、コレクション、Anki のカードとその復習履歴、対戦の指し手、そしてその行を指すゴミ箱の項目は、残った行に従います。どの対戦からも指されていない局面が修正されるのは、別のソフトウェア（XG、BGBlitz…）から持ち込んだ XGID の言葉によってだけです。その XGID の Crawford 欄がこの試合は Crawford ではないと述べ、かつその XGID がまさにこの局面を表しているときです。逆向きには、対戦のない局面が両側とも0で保存されていて、持ち込んだ XGID が 1 ポイントの対戦のものであり、かつその局面を表しているとき、1に直されます。1 ポイントの対戦の唯一の試合はゴールまであと 1 点の地点から始まるので、それは Crawford であり、インポータもそう書きます。より長い対戦の Crawford 後の DMP は0のままです。その XGID がその対戦の長さを示しているからです。blunderDB 自身が書き直した XGID は保存済みのスコアを繰り返すだけで、何も証明しません。対戦のないそれ以外の局面はそのままにされます。そのスコアが述べていることに反するものが何もないからです。

自動的に実行されることはありません。これは意図的です。データベースを開いただけで全員の分析列を書き換えたり、局面のハッシュを取り直したりするのは、道具が利用者に黙ってやってよいことではないからです。

例：

./blunderdb repair --db base.db

# 42 analyses repaired.
# 7 positions reclassified.
# 3 positions rehashed onto the right Crawford sentinel.

delete — データを削除する

マッチとすべての関連データ（ゲーム、手、分析）を削除します。

./blunderdb delete --db <path> --type match --id <id> [--confirm]

オプション：

  • --db — データベース（必須）。

  • --type — 削除の種類：match（必須）。

  • --id — 削除する要素のID（必須）。

  • --confirm — 確認なしで削除する。

  • --format — 出力フォーマット：text（デフォルト）またはjson（{"match_id": N, "deleted": true}）。

例：

# Confirmation interactive, puis sans confirmation (scripts)
./blunderdb delete --db base.db --type match --id 1
./blunderdb delete --db base.db --type match --id 1 --confirm

healthcheck — デーモンを確認する

稼働中のserveデーモン（ヘッドレスモード（サーバー）参照）に準備ができているか問い合わせます。GET /readyzリクエストを1回送り、デーモンが 200 を返せば（ストレージに到達でき、スキーマが期待されるバージョンであれば）終了コード0、それ以外（ストレージに到達できない、スキーマが古い、アドレスで何もリッスンしていない）なら1を返します。データベースファイルは一切開きません。

./blunderdb healthcheck [--addr host:port] [--timeout 2s]

オプション：

  • --addr — デーモンがリッスンするアドレス（既定はBLUNDERDB_ADDR、なければ:8080）。ホストのないアドレス（:8080）やワイルドカードホスト（0.0.0.0、[::]）はループバックインターフェースで確認します。

  • --timeout — この時間を過ぎると確認を諦めます（既定は2s）。

これはコンテナイメージのHEALTHCHECKが実行するコマンドです（distrolessイメージで、curlはありません）。cmd/serveからビルドしたserveバイナリも同じコマンドを理解します。スクリプトや systemd ユニットからも同様に使えます。

例：

./blunderdb serve --db base.db --addr 127.0.0.1:8080 &
./blunderdb healthcheck --addr 127.0.0.1:8080 && echo "démon disponible"

# ready

失敗した場合はその理由が表示され、docker inspectもunhealthyなコンテナについて同じ内容を示します：

Error: healthcheck: http://127.0.0.1:8080/readyz answered 503 Service Unavailable (version_mismatch)

mcp — データベースを AI アシスタントに提供する

Model Context Protocol を通じて、標準入出力でデータベースのツールを AI アシスタントに提供します。コマンドを起動するのはアシスタントです。ツールは、コマンドバーの文法でポジションを検索し、ポジションとその解析を読み取り、ミスを説明し、プレイヤーの統計を計算し、マッチ・トーナメント・コレクションを一覧表示し、クイズを出題します。--write を付けない限り、読み取りのみを行います。完全な一覧とデーモンの HTTP 版：AI アシスタント向けツール（MCP）。

./blunderdb mcp --db base.db [--write]

オプション：

  • --db — データベースファイル（必須）。

  • --write — 書き込みを行うツールも提供します：ポジションの保存、コメントの追加、コレクションの作成と追加。削除は一切行いません。

call と同じく、このコマンドは --write なしでも、開くときに古いデータベースのスキーマを移行します。

例： データベースを Claude Code に登録する。

claude mcp add blunderdb -- blunderdb mcp --db /chemin/vers/base.db

completion ――― シェル補完

サブコマンド名の補完スクリプトを標準出力に表示する。各スクリプトに組み込まれるコマンド一覧は、blunderdb helpやmain.goのディスパッチ（handlers()）が読み込むのと同じテーブルから生成される。そのため、新しいサブコマンドが組み込まれると同時に補完でも提供され、手作業で維持する必要は何もない。

./blunderdb completion <bash|zsh|fish>

例：

# bash
source <(blunderdb completion bash)
blunderdb completion bash | sudo tee /etc/bash_completion.d/blunderdb > /dev/null

# zsh : un répertoire déjà sur $fpath
blunderdb completion zsh > "${fpath[1]}/_blunderdb"

# fish
blunderdb completion fish | source

パッケージはこれを自動的にインストールする：.deb/.rpm（nfpm）と AUR パッケージはビルド時にパッケージ済みのバイナリから3つのスクリプトを生成し、Homebrew の cask はインストール時に一度、generate_completions_from_executableを通じてblunderdb completion <shell>を実行する。リポジトリには何もコミットされないため、補完がサブコマンドのテーブルからずれることは決してない。

version — バージョンを表示する

blunderDB のバージョンと、このバイナリが書き込むデータベーススキーマのバージョンを表示します。バグ報告に最初に添えるべき情報です。

./blunderdb version
# blunderDB version 0.36.0 (database schema 2.31.0)
